# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

SmartCart is a shopping-cart price optimizer for Argentine supermarkets (Coto, Día and Carrefour). It scrapes each store's internal API, unifies their catalogs by EAN barcode, lets a user build a cart via semantic search, and runs a constraint solver (Google OR-Tools) to find the cheapest way to split that cart across stores — accounting for promotions, bank/membership discounts, delivery costs, and each store's minimum-purchase threshold.

Full technical spec (data model, architecture rationale): `docs/smartcart_spec.md`.
Pending work and known risks, with the reasoning behind each: `docs/TODO.md`.

The repo has two halves that run as separate processes and talk over HTTP:
- **`src/`** — Python/FastAPI backend + Postgres/pgvector.
- **`frontend/`** — React/Vite/Tailwind SPA (rebuilt from an earlier Streamlit prototype; the old `frontend/app.py`/`utils.py` no longer exist).

## Commands

### Backend

```bash
docker-compose up -d              # Postgres + pgvector on localhost:5432 (db/user/pass: smartcart/smartuser/smartpassword)
pip install -r requirements.txt
cp .env.example .env              # ANALYTICS_* — without it /optimize emits no analytics event (stage 9)
uvicorn src.api:app --reload      # API on http://localhost:8000 (interactive docs at /docs)
python -m src.scripts.run_scrapers   # populate the DB: all three scrapers + embeddings
python -m src.scripts.orchestrator   # same, but the unattended path (logs + telemetry, stage 10)
./ops/run_pipeline.sh                # what cron runs: .env + venv + timeout around the orchestrator
python -m playwright install chromium # one-off, only needed by the bank-promo scrapers
python -m src.scrapers.get_bank_promos  # regenerate src/scrapers/bank_promos.json
pytest                            # whole suite
pytest tests/test_optimizer.py    # single file
pytest tests/test_api.py::test_fastapi_endpoints   # single test
```

`docker-compose.yml` only defines the Postgres container — it does not run the API or frontend.

`src/scripts/run_scrapers.py` is the **interactive** entry point for populating the DB: it runs all three scrapers over their `MVP_CATEGORIES` constants and then regenerates embeddings (products are invisible to `GET /search` until they have one). Takes `--store coto|dia|carrefour|all` and `--skip-embeddings`; a failure in one store doesn't abort the others, and a failure in one *category* no longer aborts its store (`_run_store` catches per category and reports it through `StoreRunResult.complete`, which is what gates pruning). Each scraper's `__main__` block still works standalone. Widening the catalog means adding a row to `src/shelves.py`, not editing the script — each scraper's `MVP_CATEGORIES` is now `keys_for_store(...)` over that table (see stage 1b).

`src/scripts/orchestrator.py` is the **unattended** entry point (stage 10) — same work, but with file logging, telemetry, DB pre-flight and signal handling. It imports `STORE_RUNNERS` from `run_scrapers.py` rather than reimplementing the sweep; the two share `build_arg_parser()`, so a new flag lands in both.

`src/scrapers/get_bank_promos.py` is the unrelated second runner: it regenerates the **bank discounts** (see stage 8), not the catalog. Takes `--store coto|dia|carrefour|all` and `--dry-run`. A store that fails keeps its previous block in the JSON instead of being overwritten with `[]` — same asymmetry as the catalog pruning, since an emptied block silently stops the optimizer from applying discounts that do exist.

Tests are **not** isolated unit tests: `tests/test_api.py` and `tests/test_search.py` spin up the real FastAPI app (loading the `all-MiniLM-L6-v2` sentence-transformers model, which downloads on first run) and query the actual Postgres instance, so Postgres must be up and populated for those to pass. The pure-Python suites (no DB, no model) are `test_promos.py`, `test_category_tree.py`, `test_category_tags.py`, `test_dietary_parser.py`, `test_coto_url.py`, `test_size_parser.py`, `test_coto_logistics.py`, `test_carrefour_scraper.py`, `test_optimizer_correctness.py`, `test_strategic_swaps.py`, and `test_shelves.py`. `test_search_ranking.py` needs both Postgres and the model (like `test_api.py`). `test_orchestrator.py` is pure Python too (it monkeypatches `STORE_RUNNERS` and the telemetry writer). `test_pruning.py` and `test_scraper_telemetry.py` need Postgres but not the model, and both work on synthetic identifiers (a fake `store_id`, a fresh `run_id`) so they're safe to run against a populated DB.

Two files cover the optimizer and they are not redundant: `test_optimizer.py` runs against the real DB and asserts almost nothing (its assertions are guarded by `if result["status"] == "success"`, so it passes vacuously on an empty DB), while `test_optimizer_correctness.py` monkeypatches `src.optimizer.flatten_cart_prices` with fabricated price matrices to make the solver deterministic. Put new optimizer assertions in the latter. It includes a brute-force oracle (`_brute_force_optimum`) that enumerates every assignment and replicates the solver's integer-cents arithmetic — including the truncating division on bank discounts — so scenarios can assert the exact optimum rather than "a plausible answer". Its `BANK_PROMOS` mirrors the table hardcoded in `optimize_cart`; change one and you must change the other.

`pytest.ini` sets `pythonpath = .`, so backend code is always imported as `src.module_name` (e.g. `from src.database import SmartCartDB`), never with relative imports.

## Backend architecture (`src/`)

Data flows in one direction through distinct stages — when changing behavior, know which stage owns it:

1. **Scraping** (`src/scrapers/scraper_coto.py`, `scraper_dia.py`, `scraper_carrefour.py`) — hit each retailer's internal API directly (Coto: internal BFF REST endpoint; Día and Carrefour: VTEX GraphQL `productSearchV3`), paginating per category. Each scraper iterates the category keys its store contributes to `src/shelves.py` (stage 1b) — the live catalog is narrow and deliberately the *same* narrow set in all three stores. `src/scrapers/{coto,dia,carrefour}_categories.json` are static dumps of each store's full category taxonomy (id/slug → `"Top -> Sub -> Leaf"` path string), consumed by `category_tree.py` for the mega-menu **and** by `category_tags.py` to tag products at ingest time (see stage 2). Día's and Carrefour's requests use a VTEX *persisted query* (fixed `sha256Hash`), so their returned field set is locked server-side — you cannot ask for new fields without a new hash; read anything beyond the known fields defensively with `.get()`. **Coto's price fields can be `null` with the key present**, so `float(d.get("formatPrice", 0))` never reaches its default and raises `TypeError` — read them through `_as_price()`. This surfaced only once the catalog widened past 5 categories, and it failed in the worst available way: the page loop's `except` swallowed it and `break`ed, so the category ended early with whatever it had and `_run_store` counted it **OK**. That sets `StoreRunResult.complete = True`, which is the sole gate on pruning — everything the truncated sweep never reached looks discontinued and gets deleted. **All three page loops now follow one rule: `break` only on a valid, empty page; every other early exit raises `CategoryScrapeError`** (`src/scrapers/errors.py`). Losing the category is strictly better than deleting live catalog, and `_run_store` already tolerates a failed category — which, since pruning became per-category (stage 2), no longer costs the rest of the store its prune. The rule exists because the legit end-of-category and four distinct failures all shared the same `break`, and `_run_store` cannot tell them apart: a non-200 response, a transport exception, a page that repeats already-seen SKUs (the endpoint stopped honoring `page`/`from`, so what's missing is unknowable), and exhausting `MAX_PAGES` (the empty-page cut never arrived). `scrape_category_slice` in Día and Carrefour used to `return None` on error, which the caller read as end-of-category — the exact shape of the `formatPrice: null` bug, one level up. `tests/test_scraper_truncation.py` walks each of those paths per store. Coto's product URL must be built by `build_coto_url()`, not by concatenating the API's `url` field (that field is a relative fragment with no leading slash, which is what produced the broken `https://www.cotodigital.com.ar_/R-...` links).

   **Carrefour specifics** — same VTEX platform as Día and the same `sha256Hash`, but three things are deliberately *not* copied from `scraper_dia.py`. (a) The request is a **POST with the JSON in the body** to `https://www.carrefour.com.ar/_v/segment/graphql/v1?workspace=master`, which avoids Base64-encoding the variables into a GET URL. (b) `map` is **derived** from the slug's segment count (`",".join(["c"] * len(parts))`) — the MVP mixes 2- and 3-level categories, and Día's hardcoded `"c,c"` sends fewer `c`s than `selectedFacets` on its own 3-level slugs. Relevered against the live Día endpoint on three 3-level slugs, `"c,c"` and `"c,c,c"` return **byte-identical results** (same `recordsFiltered`, same products) — VTEX resolves the filter from `selectedFacets` and the short `map` is not silently widening the result set. Deriving it is still the correct form, but Día's version is not a live bug to chase. (c) Carrefour's `link` field is **relative** (`/producto-123/p`), so `build_carrefour_url()` prefixes the domain — storing it raw reproduces the exact Coto bug above. One failure mode is unique enough to guard explicitly: a rotated persisted-query hash answers **HTTP 200 with an `errors` array and no `data`**, which the "empty page = end of category" pagination rule reads as success, closing the run with 0 products and no error in sight. `extract_search_payload()` (now in `src/scrapers/vtex.py`, shared with Día, which had no such check at all) separates the two — and it **raises** rather than returning `None`, because detecting the rotated hash and then still `break`ing was only half the fix. The taxonomy dump is regenerated with `python -m src.scrapers.get_carrefour_categories` (public VTEX endpoint `/api/catalog_system/pub/category/tree/3`).

1b. **Which shelves get scraped** (`src/shelves.py`) — one table, `SHELVES`, mapping 20 canonical shelf slugs to the per-store category keys (`catv…` id for Coto, URL slug for Día and Carrefour). The three `MVP_CATEGORIES` are `keys_for_store("coto"|"dia"|"carrefour")` over it, so a shelf is added once, for all three stores, in one row.

   **The table exists because alignment is the whole point.** Unification is by EAN (`unified_id = f"prod_{ean}"`), so a product is only comparable across stores if all three swept *the same shelf* — barrelling through more categories per store adds catalog but not comparisons. Three independent lists satisfied that by coincidence and drifted silently: nothing fails when Coto sweeps yerba and Día doesn't, the optimizer simply runs out of things to compare. Selection favours **branded packaged goods**, which is where EANs actually coincide; loose produce, the butcher counter and sliced deli use per-store internal codes and never unify.

   Each store maps to a **list** of keys, not one key, because the three taxonomies nest at different depths: Coto only exposes very fine level-3 leaves ("Papas Fritas", "Mani") while Día and Carrefour have level-2 nodes that already cover the shelf (`almacen/snacks`). Current totals: 30 Coto keys, 24 Día, 21 Carrefour.

   **The canonical shelf tag is what makes cross-store comparison usable.** `shelf_tags()` appends the shelf slug to the taxonomy path before the scrapers attach it as `tags`. Without it only **7 of the 20** shelves overlapped across all three store pairs — each chain names the same shelf differently (yerba is `Mate` at Coto, `Yerba mate` at Día, `Yerba` at Carrefour), and `filter_tags()` + Postgres `&&` compare literals, so the product ends up with no possible substitute and nothing says so. With it, 20/20 overlap. It is the alias dict stage 7 asks for; the tag is appended only when absent, so shelves whose leaf already matches (`alfajores`, `leches`) don't carry it twice. A key **outside** the table gets no shelf tag — `shelf_for_key()` returns `None` and the old behaviour stands, rather than inventing a shelf.

2. **Normalization + persistence** (`src/database.py`, `SmartCartDB`) — `save_store_products()` computes `unified_id = f"prod_{ean}"` and upserts into two tables: `unified_products` (one row per EAN, cross-store) and `store_products` (one row per store's offer, `ON CONFLICT` keyed on `(store_id, store_sku)`). Raw per-store promo payloads are normalized here via `src/promotion_parser.py`'s `PromoTransformer` (`.coto()` / `.dia()` / `.carrefour()`, the last two sharing `_vtex()`) into one of four standard promo `type`s consumed later by the flattener: `direct_discount`, `conditional_discount_flat`, `conditional_discount` (e.g. "2nd unit 50% off"), `multi_buy` (e.g. 3x2). Each product's raw scraped category also gets normalized here through `SmartCartDB.CATEGORY_MAP` into one of only 4 coarse buckets (Lácteos/Golosinas/Almacén/Otros — everything else falls to Otros) — this is the value that ends up in `unified_products.category` and is what `GET /category/{name}` filters on. There are **no migrations** in this project: the base schema was created by hand, and newer columns are added idempotently at runtime via `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` (`SmartCartDB._ensure_schema()` for `tags`/`is_gluten_free`/`is_vegan`, `EmbeddingPipeline.ensure_vector_extension_and_index()` for `name_embedding`).

   **`unit_type` holds only `'g'`, `'ml'` or `'un'` — that invariant is load-bearing.** Every consumer that compares sizes (the swap heuristic's weight band, `api.py`'s proportional suggestions) pairs identical units or `g`↔`ml` and nothing else, so a row escaping that vocabulary doesn't throw or compute a wrong number — it just stops matching anything and drops out of both features silently. Two paths used to leak: Coto's price-derived fallback for weighables (`"Tomate x Kg"`) emitted `'kg'` uncoverted, and Día's and Carrefour's equivalent fallback passed VTEX's raw `UnidaddeMedida` property straight through (`'gr'`, `'kg'`, whatever the store wrote) whenever it wasn't litres or kilos. All three now end in `size_parser.normalize_magnitude()`, which converts the value and canonicalizes the label, mapping anything unrecognized to `(1.0, 'un')`.

   Keep the two concerns separate when touching those fallbacks: the `< 1.0` branches in the VTEX scrapers decide the **magnitude** (a sub-1 quotient means `PrecioPorUnd` was per litre/kilo, not per ml/gram) and are a guess about VTEX semantics that shouldn't be changed without fresh data; `normalize_magnitude()` only decides the **vocabulary** and is idempotent over the branches' output.

   **Obsolete rows are pruned per store, only after a complete run.** `save_store_products()` only upserts, so a delisted product used to keep its `in_stock = TRUE` row forever and stay quotable — the optimizer could build an entire split around something you can't buy. `prune_missing_store_products(store_id, seen_skus)` deletes that store's rows whose SKU wasn't seen, then drops `unified_products` left with no offers at all. `run_scrapers.py` collects `seen_skus` across a store's whole category sweep and calls it only if the sweep finished: on a mid-run exception it skips pruning, because a partial sweep makes everything it didn't reach look discontinued. Two brakes, sized by the asymmetry between the two errors (a stale row is annoying, an emptied catalog is broken): an empty `seen_skus` never prunes — that's the rotated-persisted-query failure mode above, which reads as a clean run with zero products — and a delete that would take more than `MAX_PRUNE_RATIO` (30%) of the store aborts loudly. `--prune-dry-run` runs the real DELETEs and rolls back, so its reported counts are the actual ones rather than a second query that can drift from the first.

   **Every derived column must appear in the `ON CONFLICT DO UPDATE SET` list.** With no migrations, a re-scrape is the *only* mechanism for correcting bad data — so a column left out of that list is frozen at whatever the first `INSERT` wrote and can never be repaired without dropping the table. `unit_type` was omitted while its inseparable partner `total_volume_weight` was updated, which produced two failure modes worth recognizing: rows whose weight had been refreshed but whose unit still came from an older name (`"Fritolim 120 g"` stored as `'ml'`), and every product the size parser failed on staying pinned to `'un'` forever, making any later parser fix a no-op. Both are fixed, but the general rule is the point — when adding a derived column, add it to the update list in the same edit.

   **Carrefour's price gap is a member price, not a discount** — `.dia()` turns any `Price < ListPrice` into an unconditional `direct_discount`, and that rule is wrong for Carrefour: its `discountHighlights` name the gap outright (`"PROMO-Mi CRF -mfl-1-6-Dto de 6% Doble Precio"`), i.e. it's the Mi Carrefour loyalty price, and `teasers` separately advertise a `"Tarjeta Carrefour 15%"` that `Price` does *not* reflect. So `.carrefour()` scans both lists for card/loyalty wording and, when it matches, emits the discount with `requires_membership: "mi_carrefour"` — the optimizer then quotes list price by default and only unlocks the lower one for a user who declared that membership (the option exists in `ProfileDrawer`'s `MEMBERSHIP_OPTIONS`). 81 of 427 scraped rows are gated this way and none are unconditional, so treating them as open would have understated Carrefour on nearly every promoted product and won it splits that cost more at the register. Same asymmetry as the dietary flags: quoting too high only forfeits a saving, quoting too low breaks the promise the app is built on.

   **Strict aisle tags (`unified_products.tags`)** — `CATEGORY_MAP`'s 4 buckets are useless as a "same aisle" guard: it maps *leaf* labels through a 9-key dict, so across the full catalog ~98% of real categories collapse into `Otros`, putting mayonnaise and meat seasoning in the same bucket. So each product also carries `tags TEXT[]` (GIN-indexed): its full category path, slugified (`["almacen","golosinas","alfajores"]`). The path is free — `src/scrapers/coto_categories.json` is keyed by the very `category_id` `scrape_category()` receives, and `dia_categories.json` by the slug `scrape_entire_category()` receives; `src/category_tags.py` resolves it. Two rules matter when touching this: comparison uses Postgres **overlap (`&&`), never containment or branch-prefix**, and it runs over the **non-top-level** segments only (`filter_tags()`) — the stores nest at different depths (Coto `Frescos → Lácteos → Leches` vs Día `Frescos → Leches`), so a prefix filter breaks cross-store substitution exactly where it's needed, and keeping the top-level would make `almacen` match half the catalog. Products with no tags fall back to the old `category` filter, which is required as long as un-rescraped rows exist.

   **Dietary flags** — `src/dietary_parser.py` populates `is_gluten_free`/`is_vegan` from explicit phrases only. `FALSE` means "no evidence", *not* "contains gluten"; never infer these from category, and don't match the bare tokens `gluten` or `vegetal` (they'd fire on "contiene gluten" and "Sémola Vegetales"). Two rules exist because both were violated once and produced real bad data: (1) **only pass text describing that specific product** — name, brand, category path, and store-assigned structured fields (VTEX's `properties`/`clusterHighlights`); marketing `description`/`metaTagDescription` list sibling products in the same line and made a Hellmann's *ketchup* read as vegan, and no phrase rule can fix that since the claim is real but about another product. (2) Flags are **overwritten** on conflict, never `OR`-accumulated — accumulating makes them monotonic, so a false positive can never be corrected even after fixing the parser; a stale `FALSE` is safe, a stale `TRUE` is the one that hurts someone.
3. **Embeddings** (`src/embeddings.py`) — a separate offline pipeline (`EmbeddingPipeline.generate_and_save_embeddings()`) that encodes `"{brand} {name}"` per product with `all-MiniLM-L6-v2` and backfills `unified_products.name_embedding` (pgvector `vector(384)`, HNSW index, cosine ops). Run this after scraping new products, before semantic search will find them.
4. **Category tree for the mega-menu** (`src/category_tree.py`) — an unrelated, purely-in-memory concern from the 4-bucket `CATEGORY_MAP` above: it parses both `*_categories.json` taxonomy dumps and merges Coto's and Día's differently-worded categories into one tree, in three layers of increasing cost/risk: (1) normalized-text equality, (2) token-subset containment (e.g. "Golosinas" ⊆ "Golosinas y Alfajores" — the safe default for catching "X" vs "X y Z" pairs with no false positives), (3) a conservative (0.90) cosine-similarity backstop reusing the same sentence-transformers model `/search` already has loaded. A small manual alias dict (`MANUAL_SUBCATEGORY_ALIASES`/`MANUAL_TOPLEVEL_ALIASES`) is the escape hatch for real duplicates neither automated step catches. **Do not lower the 0.90 threshold to catch more merges** — empirically, genuine near-duplicate category pairs and merely-related sibling categories occupy overlapping similarity bands (e.g. a true duplicate pair scored 0.798 while a false-positive-risk sibling pair scored 0.778), so threshold tuning alone can't safely separate them; add merges via the alias dicts instead. `build_category_tree()` takes the model as a parameter (dependency injection) so tests can run without loading it.
5. **Coto delivery logistics** (`src/coto_logistics.py`) — an online, per-request lookup (not ingest, hence not under `scrapers/`) that answers two questions before the solver runs: does Coto deliver to these coordinates, and what does shipping cost. It sits between the request and the flatten/CP-SAT stages because it changes two of the solver's inputs (which stores participate, and Coto's `delivery_cost`).

   Endpoint reality, relevered against the live site — **do not trust older notes describing `www.coto.com.ar/getCobertura` or a `getCostoEnvio` POST; neither exists**. The `cotodigital*.com.ar` domains all 301 to `www.coto.com.ar`, an Angular SPA that serves its `index.html` with **HTTP 200 for any unknown path** — so a client that only checks the status code parses a web page as if it were data. That's why `_fetch_json()` requires a JSON content-type. The real route is the ATG actor the SPA itself calls: `GET /rest/model/atg/actors/cProfileActor/getCobertura?lat=&lng=`. It is **public** — no login, no cookie, no `_dynSessConf` token (verified with and without; identical responses), so there is no session handshake to perform. Its payload nests everything one level down: `{"sucursal": {"coberturaCD": 1, "codigoError": "0", "mensajeError": "-", "sucursal": "220"}}`, and the coverage rule (copied from Coto's own frontend) is `sucursal.mensajeError == "-"`.

   **There is no address-level shipping-cost endpoint.** The bundle contains zero occurrences of `costo`/`importe`, and the actors that do price delivery (`getGrillaCupos`, `getCuposHoy`, `getEntregaRapida`) all return `USER_NOT_AUTHENTICATED`: Coto's real shipping cost is a function of a logged-in user's server-side cart and chosen time slot, not of coordinates. What *is* readable anonymously is the published tariff in `getParametros2` → `ENTREGA_RAPIDA_COSTO` (3399 as of Jul 2026), which `get_shipping_cost()` uses. It is one global number, identical for every covered address — that limitation is documented, not hidden, and the UI labels a fallback as an estimate.

   The module is **fail-open** and never raises: on timeout, HTML, or a malformed payload, Coto keeps competing using the frontend's per-zone fallback cost with `source: "fallback"`. Only an affirmative "no coverage" verdict excludes the store — a third party's endpoint hiccuping must not silently delete half the catalog and hand the user a worse price. Correspondingly, `check_coverage()` distinguishes `ok=False` ("couldn't determine") from `covered=False` ("Coto said no"), and **only successful lookups are cached**, so a timeout doesn't pin the fallback for the whole 30-minute TTL.

   Related but deliberately untouched: `getParametros2` also exposes `MINIMOGENERAL = 30000`, against the `15000` hardcoded for `coto_online` in `optimize_cart`'s `DEFAULT_MIN_SPEND_LIMITS`. It was not confirmed that these are the same concept, and changing it flips which carts come back infeasible — treat as an open question, not a bug to fix in passing.
6. **Search & optimization API** (`src/api.py`) — FastAPI app; loads the sentence-transformers model and builds the category tree once at startup (`lifespan`, stored in the `ml_models` dict). Endpoints:
   - `GET /search?q=` — pgvector cosine-distance nearest-neighbor over `name_embedding`, **retrieve-then-rerank in one query**: a `pool` CTE takes the `SEARCH_POOL_SIZE` (100) nearest by pure distance — the only ordering the HNSW index can accelerate — then the outer query reorders that pool by `distance − STORE_BONUS × LEAST(GREATEST(store_count−1,0), STORE_BONUS_CAP)` and cuts to `limit`.

     **The pool must be larger than `limit`, and that is the whole point.** Pure distance gave a product stocked by all three stores no edge over one sold in a single store, which for a price-comparison app leaves results the optimizer can do nothing with at the top. It cannot be fixed client-side: the browser only receives the `limit` rows Postgres already chose, so a 3-store product at rank 25 does not exist for it — reordering there changes the *order* of the top-N but never its *composition*.

     **`hnsw.ef_search` defaults to 40 and is a ceiling on rows the index returns**, so `LIMIT 100` silently yields 40 and the rerank permutes the same 40 candidates forever — the feature looks alive and does nothing. It is raised per connection via `SELECT set_config('hnsw.ef_search', …)`; plain `SET` cannot take a bind parameter. `tests/test_search_ranking.py` asserts the pool comes back at full size, which is what makes that failure loud.

     **`STORE_BONUS = 0.01` is calibrated, not guessed, and must not be raised to "catch more".** Over 15 real catalog queries the natural top-20 spread (d@20 − d@1) has median 0.110, so the cap makes the worst-case relevance loss `STORE_BONUS × STORE_BONUS_CAP` = 0.02, ~18% of it; measured effect is 5% of the top-20 changing and mean store count 1.49 → 1.57. At 0.02 the query `yogur bebible` drops two actually-*bebible* yogurts (d=0.368, 0.370) for three 3-store Yogurísimo *Griego* (d≈0.39) — the embedding does not treat "bebible" as a hard constraint, so a moderate bonus buys availability with literal relevance. At 0.05 a product can climb from rank 79, clearing the entire rank-20→100 relevance gap (0.105). Same discipline as the 0.90 in stage 4: bound it by the damage it must not cause. Band-based ranking (`ORDER BY floor(d/w), …`) was measured too and gives identical numbers at equal conservatism, so the capped linear bonus wins on simplicity.

     `distance` is returned **raw**, never the ranking score — it is semantic relevance, and folding the bonus in would make the field unreadable. `store_count` counts only `in_stock` offers while `available_at_stores` carries them all, so the two can legitimately disagree.
   - `GET /categories` — the flat 4-bucket list from `CATEGORY_MAP`.
   - `GET /categories/tree` — the merged Coto+Día taxonomy from `category_tree.py`, for the mega-menu. Its `has_direct_category_match` flag per top-level node tells the frontend whether to route a click to `GET /category/{name}` (exact match against the 4-bucket column) or fall back to `GET /search?q=<label>` (nearly always, since the coarse column only covers 3 of ~15 real top-levels).
   - `GET /category/{name}` — unlike `/search`, this one also computes `min_price` and picks a best-available `image_url` per product; it orders by `store_count DESC, name ASC`, which costs nothing here because its `distance` is a hardcoded `0.0` — there is no relevance to trade away — and fixes a real defect: the query had **no `ORDER BY` at all**, so `LIMIT 50` returned whichever 50 rows Postgres had at hand and two identical calls could answer with different products; `/search`'s response omits both (a known, pre-existing gap predating this API's current shape — not something to "fix" incidentally). Note `min_price` is the minimum of the **list** prices, promos ignored — the frontend treats it as a fallback, not as the price to display (see `resolveDisplayPrice` below).

     Both endpoints build their offers through the shared `_build_store_offer()`, which also fills `promo_unit_price`/`promo_description` per offer: the net unit price **at quantity 1**, computed by `src/flattener.py`'s `evaluate_best_promo()` — the same evaluator the optimizer uses, never a reimplementation. Evaluating at `q=1` is what makes the grid's semantics fall out for free: a `direct_discount` applies from the first unit, while the three conditional types are gated behind `q >= required_quantity` and therefore leave `promo_unit_price` at `None` until the user raises the quantity (at which point `POST /price-preview` takes over). It is called with **no memberships**, since the grid is anonymous and a card-gated promo must not be advertised as the default price. `None` also covers the case of a promo whose `discount_price_per_unit` equals `base_price` — real in the current data, and not something to announce.
   - `GET /logistics/coto/coverage?lat=&lng=` — thin wrapper over `check_coverage()` so the frontend's address onboarding can warn immediately that Coto doesn't reach an address, instead of the user finding out only after building a cart.
   - `POST /optimize` — the core flow: optional `lat`/`lng` first go through `resolve_coto_logistics()` (stage 5), which may add `coto_online` to `excluded_stores` or overwrite its `delivery_cost`; then `src/flattener.py`'s `flatten_cart_prices()` "flattens" each cart line into its cheapest net cost per store for the requested quantity (evaluating all applicable promos, gated by `user_memberships`), and `src/optimizer.py`'s `optimize_cart()` builds a CP-SAT model (`ortools`) with one boolean var per (product, store) pair plus a per-store "active" var, enforcing each store's minimum-spend threshold as a hard constraint and minimizing total cost (subtotal + delivery − capped bank-card discount). Returns HTTP 400 with a human-readable `detail` when infeasible. The response carries a `logistics.coto` block (`covered`/`sucursal`/`delivery_cost`/`source`/`message`) and `excluded_stores` so the UI can explain a missing store rather than leaving it looking merely expensive.

     **Registering a store is a two-file change, always in the same commit.** `optimize_cart` derives its store list from the keys of `min_spend_limits` (`DEFAULT_MIN_SPEND_LIMITS`) and then indexes `delivery_costs[store]` with **no default**, while the request's `delivery_costs` comes from the frontend's per-zone table. Adding a key to one side only either crashes `/optimize` with a `KeyError` (optimizer knows the store, frontend doesn't send it) or silently benches the store (frontend sends it, optimizer's limits don't list it) — and in that second case, a cart item sold *only* there hits the `sum([]) == 1` trap below and comes back infeasible blaming minimum spend. Carrefour is `carrefour_online`: min spend $20.000, flat $3.500 delivery in all four zones. It used to have **no `bank_promos` entry** because its discounts are day-specific and the model has no notion of day; stage 8's loader now filters to the current weekday before the table ever reaches the solver, so Carrefour participates with no special case. Carrefour has no coverage/tariff endpoint of its own, so unlike Coto it always uses the per-zone cost.

     Excluding a store is **not** the same as making it expensive: `optimize_cart(excluded_stores=[...])` drops it from `stores` entirely. That creates a trap worth knowing — a product sold only by the excluded store loses every one of its boolean vars, turning its assignment constraint into `sum([]) == 1`, which the solver reports as plain infeasible and the API would then blame on minimum-spend ("add more products"), advice that cannot possibly help. `optimize_cart` therefore detects those products *before* building the model and returns `unavailable_products` with a message naming the real cause. The single-store baselines in `api.py` are filtered by `excluded_stores` too, since a baseline for a store that can't deliver compares against an impossible purchase. Post-solve, `api.py` also computes single-store baselines for comparison (a separate, simpler calculation — not routed through the solver, so it can legitimately diverge from the optimizer's own numbers), semantic "smart replacement" suggestions (nearest-neighbor by embedding within the same category, ≥20% cheaper for equal weight), and — when Día is part of the split — a VTEX "magic link" checkout URL (`generate_vtex_magic_link`).
7. **Store-closure heuristic** (`src/strategic_swaps.py`) — post-solve, answers a question the solver structurally cannot: *should a whole store be dropped by substituting the products only it carries?* CP-SAT is optimal, but over a space where cart products are immutable, so five Carrefour-exclusive items force `y[carrefour] = 1`, and an open store drags its $20.000 minimum plus a second delivery. `find_strategic_swaps()` finds each active store's **anchors** (products with no offer in any other non-excluded store), pulls same-aisle semantic replacements, and re-runs the solver on the substituted cart with that store excluded. Result lands in `strategic_swaps` on the `/optimize` response (always present on `success`; `[]` is the normal case).

   Four rules, each load-bearing. (a) **The what-if calls `optimize_cart()`, it does not recompute cost** — hand-rolling "subtotal + delivery − bank discount" would mean another copy of the `bank_promos` table and a second arithmetic beside the model's integer cents with its truncating division; a saving computed differently from the total already shown to the user is a guaranteed silent bug. `optimize_cart` grew an optional `flat_prices=` for this (pass it **filtered to that cart's UIDs** — `products` comes from its keys, so a stray UID becomes a phantom with its own `== 1` constraint). (b) **A store with zero anchors is skipped without a single query** — closing it was already a feasible point the optimal solver evaluated and rejected, so the simulation cannot win; the heuristic only adds value where substitution leaves the solver's search space. Note this is a test on *anchors*, not on how many stores are in the split: a **single-store split must still be analysed**, and is in fact the worst case. One cheap exclusive product forces its store open, that store's minimum then drags the entire rest of the cart in behind it, and the split collapses to one store — the real report that caught this was a $1.550 Carrefour-only vinegar pulling 15 alfajores in at $2.125 to clear the $20.000 minimum when Coto had them at $1.062,50 on promo ($36.925 vs $15.750). An early `len(split) < 2` guard read that shape as "nothing to close" and suppressed the alert on exactly the carts that needed it most. (c) Anchors are computed against **non-excluded** stores, not *active* ones: closing a store lets the solver switch on one that was off, so a product that store also carries relocates by itself and needs no swap. (d) Replacements are **strict** — same aisle via `same_aisle_filter`, compatible unit, and weight within 0.5x–2x — because without a size band the heuristic "saves" money by shrinking the cart; comparability gates the candidate, but the simulation prices the **real** cost, never a weight-prorated one. It is all-or-nothing per store (one unreplaceable anchor kills the closure), fail-open like `coto_logistics.py`, and lives behind its own `try/except` in `api.py` so a failure here can't take down `single_store_baselines` and `suggestions` the way the surrounding broad `except` would.

   Two constraints on candidate selection exist because violating them corrupts the simulation silently: a candidate **already in the cart** and two anchors sharing **one** replacement both produce a duplicated `unified_id`, and `flatten_cart_prices` resolves quantity with the last occurrence while `optimize_cart` uses the first — the simulated cost would correspond to no real cart. Candidates are also priced at the **anchor's quantity**, grouped into one flatten call per distinct quantity, since conditional promos (3x2, 2nd unit 50%) only unlock above a threshold.

   **Multipacks are compared, never multiplied.** `extract_pack_count()` gates candidates so a six-pack is only ever swapped for another six-pack. It deliberately does *not* multiply the weight, and that is not laziness: relieved against the real catalog, the number next to the `xN` is sometimes the pack total (`"X6 ALFA PAMPA 360g"`, `"x6 244 grs"`) and sometimes the per-unit size (`"Entre Dos x6 45 g."`, `"Chocoarroz x6 36 grs"`), with nothing in the name to tell them apart. Multiplying would inflate exactly the rows that already carried the total, and an inflated weight *lowers* price-per-gram — the product would look like a bargain and get recommended. Same asymmetry the dietary flags follow: erring expensive forfeits a saving, erring cheap breaks the promise.

   Both this and `api.py`'s suggestions rely on `unit_type` holding only `'g'`/`'ml'`/`'un'` — see the unit-vocabulary invariant in stage 2.

   **The store-vocabulary gap is closed by the canonical shelf tag** (stage 1b): every product also carries its shelf slug, identical across the three stores, so `&&` matches by construction for anything inside the scraped table. What follows is the shape of the problem it solves, and still describes any category scraped outside that table.

   **Known gap (outside `src/shelves.py`): the aisle filter is store-vocabulary-sensitive.** `tags` come from each store's own taxonomy, and the stores don't always name the same shelf the same way — Carrefour files vinegar under `almacen → aceites-y-vinagres`, Día under `almacen → aceites-y-aderezos`. Those don't overlap, so `&&` rejects the pair and a Carrefour vinegar can never be matched against the Día vinegar that is its closest embedding neighbour (measured: `Vinagre de Vino DIA 500 Ml.` sits at distance 0.350 from the Carrefour Bulnez, nearer than any candidate the filter does admit). This is the price of the strictness that keeps mayonnaise away from meat seasoning, and it fails safe — a missed swap forfeits a saving, it doesn't propose a wrong one. `category_tree.py` solved the analogous problem with `MANUAL_SUBCATEGORY_ALIASES`; for `tags` the equivalent is `src/shelves.py`'s canonical shelf tag (do **not** loosen `&&` to a similarity threshold — see the 0.90 discussion in stage 4).

8. **Bank discounts** (`src/promotions/`, `src/bank_promos.py`) — an offline pipeline, unrelated to stage 1's catalog scraping: it relieves the **card/wallet discounts each chain publishes for the whole store**, which hang off no product and land in a JSON file, not Postgres. It exists because `optimize_cart` used to hardcode a two-row table (Galicia 20% at Coto, Macro 15% at Día) that was stale and had no notion of day.

   `DiscountScraper` (ABC) is a template method: `scrape()` fixes the whole lifecycle (fetch → iterate → translate → validate → dedupe → report) and is **not** overridden; subclasses supply only `_fetch_raw`/`_iter_raw_promos`/`_to_discount`. Discarding is centralized there on purpose — it's the part of scraping that breaks silently, and three subclasses filtering on their own would mean three criteria and no count of what was thrown away (`self.discards` is a Counter the runner prints). All three emit the same frozen `BankDiscount` dataclass, which validates in `__post_init__`; an invalid record is dropped with a log, never repaired.

   **The transport is deliberately not uniform.** `CotoScraper` uses `httpx` against `getPromocionesMulticanal`, a public ATG actor — verified with a valid `_dynSessConf`, a bogus one, and none at all: byte-identical responses, so **the token is not hardcoded** (same finding as stage 5). Día and Carrefour render their grids client-side with no JSON equivalent, so they subclass `PlaywrightScraper`, which owns the browser lifecycle and **imports playwright lazily inside the method** — that's what keeps `CotoScraper` and the API working on a machine with no Chromium.

   Per-store specifics worth knowing: Coto's bank name is in **no field** (`banco` is a numeric code reused across unrelated promos), so identity comes from the logo filename (`logo_naranjax2.png`) — which is why `banks.py`'s alias boundary blocks letters but **allows digits**, since a `\b` would reject every versioned icon. Día's days come from **clicking the day tabs** and recording which cards appear, not from parsing prose, and its "Ver Legales" is a real modal that captures pointer events — leaving it open breaks every subsequent card, hence open→read→close. Carrefour needs no clicking (the legal is already in the DOM, just collapsed) but has two traps: its big number is the **installment count** on financing cards ("6" in "Hasta 6 Cuotas"), so financing is filtered *before* reading it, and only cards carrying the `logoOnline` icon apply to web purchases (13 of 32 are store-only).

   `legal_parser.py` is pure and holds the rules that were each learned from a real text: caps are read only when a tope word precedes the amount, **worked examples are stripped first** (Columbia's "EJEMPLO: ... REINTEGRO DE $200" made the min-rule report a $200 cap instead of $10.000), ties take the **lower** cap, and `parse_money_ars` reads `.` as a thousands separator — the opposite of `coto_logistics.parse_amount`, whose back-office rule turns `$12.000` into 12. Percentages have a `strict` mode for long legals so financing rates ("CFT 0%", "T.N.A. 0,00%") can't pass as discounts.

   **The loader filters by weekday, and that's the load-bearing part.** CP-SAT has no notion of day, so `load_bank_promos(today)` emits only what's valid now — which is what let Carrefour into the table at all (see stage 6). It also **sorts by descending percentage**, because `optimize_cart` picks the *first* matching card, not the best, and real data has three Naranja X tiers at Coto. It is fail-open: a missing or corrupt file returns `FALLBACK_BANK_PROMOS` (the old hardcoded table, now the single source both the optimizer and `test_optimizer_correctness.py` import, so the two copies can no longer drift). An empty day legitimately returns `{}` — falling back there would invent a discount that isn't running.

   **Adding an entity is a two-file change.** `banks.py`'s slugs must exist in `ProfileDrawer.jsx`'s `CARD_OPTIONS`/`MEMBERSHIP_OPTIONS`, since `optimize_cart` compares by exact equality — a scraped bank the UI doesn't offer can never be activated. `MEMBERSHIP_ENTITIES` decides which of the two lists a slug belongs to (`is_membership` on the promo), because loyalty programs like Comunidad Coto travel in `user_memberships`, not `user_cards`.

9. **Analytics emitter** (`src/analytics.py`) — fires one `cart_optimized` event per optimization at **SmartCart Performance Analyzer** (`../SmartCart Performance Analyzer`), a separate service with its own Postgres warehouse on `:5433` and ingest API on `:8001` that feeds Power BI. The contract lives over there (`src/models.py`, rejects violations with 422) and is nearly 1:1 with what `optimize_cart()` already returns — `status`, `total_spent_net`, `split` and `excluded_stores` have the same names and shapes — so `build_cart_optimized_event()` forwards and computes nothing. The aggregates are the analyzer's job (`repository.py` there); recomputing them here would be a second definition that drifts silently.

   **The overriding invariant is that analytics can neither break nor slow `/optimize`.** Everything with I/O runs in a `BackgroundTask` with a 2s timeout inside a `try/except` that only logs — fail-open, same as `coto_logistics.py`. Two rules fall out of it and both are load-bearing:

   **`BackgroundTasks` does not survive a `raise HTTPException`.** FastAPI attaches the tasks to the response *after* the endpoint returns (`fastapi/routing.py`, `if raw_response.background is None`); if it raises, the exception handler builds a different response with `background=None` and the task never runs. That's why `optimize_shopping_cart`'s infeasible branch **returns `JSONResponse(status_code=400, content={"detail": msg})` instead of raising** — byte-identical on the wire to what the default handler produced, so `optimize.js`'s 400 branch is unaffected. "Cleaning this up" back to a `raise` silently drops every infeasible event, which is exactly the friction KPI (`% carritos inviables`) the integration exists to measure. Both exits emit; the `HTTPException(500)` from an engine failure deliberately does not.

   **Config comes from a `.env`, never from the shell.** `load_dotenv()` runs at import (it does not override already-exported vars, so a manual `$env:` still wins). The reason is specific: `uvicorn --reload` reloads *code* but never the *environment* — the worker inherits the parent's `os.environ` frozen at launch — so a server started before the variables existed runs the new code and emits nothing. Missing `ANALYTICS_API_KEY` means no emission by design (a dev without the analyzer must not be spammed), which makes a misconfigured server look identical to a healthy one; `analytics_status()` and `check_analyzer_health()` exist only to break that tie, reported once in `lifespan` and exposed in `GET /`. Diagnosing this cost a forensic session once already.

   Note `unavailable_products` and other unknown keys ride along fine: the analyzer's models are `extra="allow"` and keep the whole event in `raw_payload`. The frontend side is one field — `anon_user_id`, a `crypto.randomUUID()` minted and migrated into `smartcart_profile_v1` by an effect in `ProfileContext` (the key is **not** versioned; the effect *is* the migration) — plus `zone`, which travels explicitly because a `delivery_costs` dict can't be mapped back to a zone label.

10. **Orquestación desatendida** (`src/scripts/orchestrator.py`, `src/logging_setup.py`, `src/scraper_telemetry.py`, `ops/`) — the cron path around stage 1. It adds **only** operations concerns: the sweep itself stays in `run_scrapers.py`, whose `STORE_RUNNERS` the orchestrator imports. Registering a store there is still one entry.

    **Telemetry rows open before the work, not after.** `ScraperTelemetry.step()` INSERTs the row as `RUNNING` and UPDATEs it on exit, one row per step (`coto`/`dia`/`carrefour`/`embeddings`) keyed by a shared `run_id`. A single INSERT at the end would be simpler and would lose exactly the case worth catching: killed by the watchdog, OOM, reboot. Those leave no row at all, which is indistinguishable from "cron never fired" — whereas a stranded `RUNNING` row says precisely what happened. `start_time` comes from Python, not `now()`, so `duration_seconds` measures the step and not the round-trip. The writer is fail-open on its own connection (same doctrine as `coto_logistics.py` and `analytics.py`): observability must not be able to break what it observes.

    **`status` semantics are load-bearing** — `SUCCESS` needs every category *and* an un-aborted prune; `PARTIAL` is ≥1 category OK with either a failed category or a `skipped` prune; `FAILED` is zero categories OK. A skipped prune counts as PARTIAL on purpose: both of its brakes (zero SKUs seen, or a delete exceeding `MAX_PRUNE_RATIO`) only fire on the signature of a broken scraper, so a dashboard that paints that green hides the one thing worth looking at.

    **`save_store_products()` now raises instead of swallowing** (it used to `print` the error and return normally). That `except` never saved any data — psycopg3 already wrapped the batch in a transaction, so a mid-batch error had rolled the category back regardless — it only hid the loss: with Postgres down the run reported success with zero rows written, then pruned against a `seen_skus` that never landed. Its return value is now the row count. Side effect accepted: the scrapers' `__main__` blocks abort with a traceback rather than continuing.

    **Logging deliberately avoids `TimedRotatingFileHandler`.** That handler rotates only while the process is alive across midnight; a job that starts at 03:00 and runs for minutes never crosses it, so it would append to one unbounded file forever. For a short daily process the correct rotation is the date in the filename (`logs/orchestrator_YYYYMMDD.log`) plus an explicit retention sweep. A `logging.Filter` stamps the `run_id` on every record — including third-party loggers — so one run is a `grep` and cross-references its telemetry rows.

    `ops/run_pipeline.sh` is self-locating (no hardcoded paths), sources `.env`, activates the venv by absolute path, `cd`s to the repo root (`pytest.ini` sets `pythonpath = .`, so `python -m src.…` requires it) and runs under `timeout --signal=TERM --kill-after=60s` — TERM first so `SIGTERM` reaches the orchestrator's handler and closes the open telemetry row. It needs the timeout because `scraper_dia.scrape_entire_category` has no page cap, unlike Carrefour's `MAX_PAGES = 60`. Because `.env` is `source`d by the shell, `DATABASE_URL` is documented in **URL form** — libpq form (`host=… port=…`) has spaces and the shell would split it into commands. `ops/crontab.example` carries the `flock -n` line (escaped `\%`, lockfile in `/tmp` never under `/mnt/c` where WSL's 9p gives no reliable lock semantics) and the WSL-specific caveats that break the job for reasons unrelated to the code: cron isn't started by default, and **WSL must be running at 03:00 or the job simply never fires** — no script fixes that; the documented alternative is a Windows Task Scheduler entry invoking `wsl.exe`.

    Exit codes are the monitoring contract: `0` all SUCCESS · `1` any PARTIAL/FAILED · `2` startup failure (Postgres unreachable — no scrapers ran, and no telemetry either, since there's nowhere to write it) · `124` watchdog timeout · `143` SIGTERM.

## Frontend architecture (`frontend/src`)

Plain React state (Context + `useReducer`/`useState`, no Redux/Zustand/React Query) and native `fetch` (no axios) — deliberate choices for an app this size; don't introduce a state/data-fetching library without a concrete reason. Tailwind is v4, configured CSS-first (theme tokens live in `src/index.css` under `@theme`, not in a `tailwind.config.js`/`postcss.config.js`, which don't exist in this project).

- `api/` — thin `fetch` wrappers per resource (`products.js`, `categories.js`, `optimize.js`) over `api/client.js`'s `apiFetch`/`ApiError`. `optimize.js`'s `optimizeCart()` deliberately catches the backend's 400 "infeasible" response and returns `{ok: false, detail}` instead of throwing, since that's an expected outcome the UI renders inline, not an error state.
- `context/` — `CartContext` (`{unified_id: {name, quantity}}`, persisted to `localStorage`, mirrors the shape the old Streamlit prototype used) and `ProfileContext` (bank cards, memberships, and the geocoded `location`). `ProfileContext` derives `coordinates` (null when the user skipped the address) for `POST /optimize`.

  **Delivery zone is derived, never asked.** There is no `profile.zone` and no zone dropdown — that selector was removed because it let a user hold an address in San Isidro while declaring "CABA", and the declared value is what priced the shipping. `utils/deliveryCosts.js`'s `resolveZoneFromAddress()` maps Nominatim's structured `address` (which `geocodeAddress()` had been requesting via `addressdetails=1` and discarding) onto one of the four zones, and `LocationModal` persists the result as `location.zone`. Its `PARTIDO_ZONES` table is **data, not logic**: a missing partido is a one-line fix. The three shapes it handles were relevered against live responses — CABA arrives as `state: "Ciudad Autónoma de Buenos Aires"`, GBA as `state: "Buenos Aires"` plus `state_district: "Partido de X"`, and sometimes GBA omits `state_district` and only has `city`. Returning `null` means "unknown", not an error: `getDeliveryCostsForZone()` already falls back to the first zone, which covers addresses outside AMBA, map-picked points whose reverse geocoding failed, and profiles saved before the field existed.

  The per-zone table is **not** dead weight next to `coto_logistics.py`: it is the *only* source of Día's and Carrefour's shipping cost (neither has a coverage or pricing endpoint at all), and Coto's fallback when there are no coordinates or its site is unreachable. Carrefour's number repeats across the four zones because its tariff really is flat, not because the rows are unfinished. `delivery_costs` must therefore keep travelling in the `POST /optimize` body with **all three** store keys — `src/optimizer.py` indexes `delivery_costs[store]` for every store in `min_spend_limits` (a missing key is a `KeyError`, not a default) and `src/api.py` derives the baseline store list from its keys.
- **Address onboarding** — `components/onboarding/LocationModal.jsx` blocks the app from `App.jsx` whenever `profile.location` is falsy, geocoding through `api/geocoding.js` (Nominatim). The same modal doubles as the change-address flow, opened from the `MapPin` chip in `Header.jsx` and from `AddressField`'s "Cambiar" button in the cart's `ProfileDrawer` — those two are the only location controls in the app. (`AddressField` used to call a `clearLocation()` that wiped the address to force the *blocking* onboarding modal; both that helper and the trap it created — changing your mind left you with no address and no way out — are gone.) The `onClose` prop is the **only** thing that distinguishes the two modes: with it the modal is dismissable (X / Escape / backdrop) and preloads the current point onto the map; without it, onboarding stays blocking, because closing it there would leave the app in neither of the two valid states (an address, or `{skipped: true}`). `App.jsx` owns that open state so there is still exactly one place that knows how to geocode. Nothing extra is needed to re-filter the catalog after a change: `setLocation` always overwrites `storeCoverage`, which recomputes `unavailableStores`, which the grid already reads. Two constraints there are deliberate: the search fires on **explicit submit, never per keystroke** (Nominatim's policy is 1 req/s; an autocomplete violates it immediately and risks an IP ban), and it presents **multiple candidates for the user to pick** rather than auto-taking the first hit, since duplicate street names across partidos would otherwise silently bind the session to the wrong sucursal. The modal has an escape hatch ("seguir sin dirección"), because Nominatim being down must not render the app unusable; skipping stores `{skipped: true}`, which is distinct from `null` (never onboarded) and falls back to per-zone costs. Adding `location` did **not** version the `smartcart_profile_v1` localStorage key on purpose: pre-existing profiles simply lack the field, land on `undefined`, and get the modal — which is the desired behavior.
- `hooks/useProductFilters.js` — the participating stores live once in `utils/constants.js`'s `STORES` (id + label); `StoreAvailabilityToggle` draws the checkboxes from it and this hook derives the filter's neutral state from it, so adding a store is one entry rather than three hand-written key literals. All product-listing facets (brand, price range, store availability, sort) are derived 100% client-side over an already-fetched result array; there's no server round-trip per filter change (unlike the Carrefour reference this UI's layout is modeled on), so there's intentionally no "Apply" button. Price bounds/sorting go through `utils/formatters.js`'s `resolveDisplayPrice()` rather than raw `product.min_price`, so the grid sorts by the price it actually shows. That helper takes the cheapest `promo_unit_price ?? base_price` across `available_at_stores` and only falls back to `min_price` when no offer has a usable price — the order matters: `min_price` is list-price-only and `GET /search` doesn't send it at all, so preferring it (as an earlier version did) hid every direct discount. `stripUnavailableStores()` nulling `min_price` stays compatible with that fallback.
- **Cart coverage warning** — `hooks/useUnavailableCartItems.js` + `components/cart/CoverageWarning.jsx` tell the user which cart items only exist at a store that can't deliver. `CartContext` stores just `{name, quantity}`, so the store map comes from reusing `POST /price-preview` (whose response is already keyed `unified_id → store_id`), and only when `unavailableStores` is non-empty — the common case costs zero requests. Two rules: it **never mutates the cart** (a mistyped address must not delete what the user picked; the optimizer reports the same products as `unavailable_products` anyway), and a `unified_id` **absent** from the response is not flagged — `/price-preview` filters by `in_stock`, so absence means "out of stock everywhere", not "doesn't reach you".
- `components/megamenu/` — routing rule for any click (top-level, subcategory, or leaf) comes from the backend's `has_direct_category_match` flag (see `/categories/tree` above): `/categoria/:bucket` (→ `GET /category/{name}`) when true, otherwise `/buscar?q=` (→ `GET /search`).
- `components/optimize/` — renders `POST /optimize`'s response; `BaselineComparison` explicitly handles the case where the "optimized" split costs *more* than a single-store baseline (splitting across stores duplicates delivery cost, which can outweigh per-item savings on small carts) — don't assume savings is always positive there. `LogisticsNotice` reads the `logistics.coto` block: without it, a missing Coto is indistinguishable from an expensive Coto, and it also surfaces `source: "fallback"` so an estimated shipping cost is never displayed as if it were the live tariff.
- Routes (`App.jsx`): `/` (home), `/buscar` (search results, reads `?q=`), `/categoria/:bucket` (category results), `/carrito` (cart + profile inputs + optimize flow, in that order since profile fields are only consumed at optimize-time).
