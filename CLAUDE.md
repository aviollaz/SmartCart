# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

SmartCart is a shopping-cart price optimizer for Argentine supermarkets (Coto, Día and Carrefour). It scrapes each store's internal API, unifies their catalogs by EAN barcode, lets a user build a cart via semantic search, and runs a constraint solver (Google OR-Tools) to find the cheapest way to split that cart across stores — accounting for promotions, bank/membership discounts, delivery costs, and each store's minimum-purchase threshold.

Full technical spec (data model, architecture rationale): `docs/smartcart_spec.md`.
Pending work and known risks, with the reasoning behind each: `docs/TODO.md`.

The repo has two halves that run as separate processes and talk over HTTP:
- **`src/`** — Python/FastAPI backend + Postgres/pgvector.
- **`frontend/`** — React/Vite/Tailwind SPA (rebuilt from an earlier Streamlit prototype; the old `frontend/app.py`/`utils.py` no longer exist).

## Commands

### Backend

```bash
docker-compose up -d              # Postgres + pgvector on localhost:5432 (db/user/pass: smartcart/smartuser/smartpassword)
pip install -r requirements.txt
cp .env.example .env              # ANALYTICS_* — without it /optimize emits no analytics event (stage 9)
uvicorn src.api:app --reload      # API on http://localhost:8000 (interactive docs at /docs)
python -m src.scripts.run_scrapers   # populate the DB: all three scrapers + embeddings
python -m src.scripts.orchestrator   # same, but the unattended path (logs + telemetry, stage 10)
sudo systemctl start smartcart-scrape.service   # how it runs in production (stage 10)
python -m playwright install chromium # one-off, only needed by the bank-promo scrapers
python -m src.scrapers.get_bank_promos  # regenerate src/scrapers/bank_promos.json
python -m src.scripts.medir_busqueda    # relevance baseline for /search (TODO item 4)
python -m src.scripts.repair_coto_urls --dry-run  # one-shot: sanitize stored Coto product_url
docker build -t smartcart-api . && docker run -p 8080:8080 -e DATABASE_URL=... smartcart-api
pytest                            # whole suite
pytest tests/test_optimizer.py    # single file
pytest tests/test_api.py::test_fastapi_endpoints   # single test
```

`docker-compose.yml` only defines the Postgres container — it does not run the API or frontend.

`src/scripts/run_scrapers.py` is the **interactive** entry point for populating the DB: it runs all three scrapers over their `MVP_CATEGORIES` constants and then regenerates embeddings (products are invisible to `GET /search` until they have one). Takes `--store coto|dia|carrefour|all` and `--skip-embeddings`; a failure in one store doesn't abort the others, and a failure in one *category* no longer aborts its store (`_run_store` catches per category and reports it through `StoreRunResult.complete`, which is what gates pruning). Each scraper's `__main__` block still works standalone. Widening the catalog means adding a row to `src/shelves.py`, not editing the script — each scraper's `MVP_CATEGORIES` is now `keys_for_store(...)` over that table (see stage 1b).

`src/scripts/orchestrator.py` is the **unattended** entry point (stage 10) — same work, but with file logging, telemetry, DB pre-flight and signal handling. It imports `STORE_RUNNERS` from `run_scrapers.py` rather than reimplementing the sweep; the two share `build_arg_parser()`, so a new flag lands in both.

`src/scrapers/get_bank_promos.py` is the unrelated second runner: it regenerates the **bank discounts** (see stage 8), not the catalog. Takes `--store coto|dia|carrefour|all` and `--dry-run`. A store that fails keeps its previous block in the JSON instead of being overwritten with `[]` — same asymmetry as the catalog pruning, since an emptied block silently stops the optimizer from applying discounts that do exist.

Tests are **not** isolated unit tests: `tests/test_api.py` and `tests/test_search.py` spin up the real FastAPI app (loading the `all-MiniLM-L6-v2` sentence-transformers model, which downloads on first run) and query the actual Postgres instance, so Postgres must be up and populated for those to pass. The pure-Python suites (no DB, no model) are `test_promos.py`, `test_taxonomy.py`, `test_dietary_parser.py`, `test_coto_url.py`, `test_size_parser.py`, `test_coto_logistics.py`, `test_carrefour_scraper.py`, `test_scraper_truncation.py`, `test_scraper_ingest_keys.py`, `test_unit_price.py`, `test_optimizer_correctness.py`, `test_strategic_swaps.py`, `test_substitutions.py`, and `test_shelves.py`. `test_search_ranking.py` needs both Postgres and the model (like `test_api.py`). `test_orchestrator.py` is pure Python too (it monkeypatches `STORE_RUNNERS` and the telemetry writer). `test_pruning.py`, `test_scraper_telemetry.py` and `test_schema.py` need Postgres but not the model. The first two work on synthetic identifiers (a fake `store_id`, a fresh `run_id`) so they're safe to run against a populated DB; `test_schema.py` only re-emits the idempotent DDL and reads the Postgres catalog, so it never touches data.

Two files cover the optimizer and they are not redundant: `test_optimizer.py` runs against the real DB and asserts almost nothing (its assertions are guarded by `if result["status"] == "success"`, so it passes vacuously on an empty DB), while `test_optimizer_correctness.py` monkeypatches `src.optimizer.flatten_cart_prices` with fabricated price matrices to make the solver deterministic. Put new optimizer assertions in the latter. It includes a brute-force oracle (`_brute_force_optimum`) that enumerates every assignment and replicates the solver's integer-cents arithmetic — including the truncating division on bank discounts — so scenarios can assert the exact optimum rather than "a plausible answer". Its `BANK_PROMOS` mirrors the table hardcoded in `optimize_cart`; change one and you must change the other.

`pytest.ini` sets `pythonpath = .`, so backend code is always imported as `src.module_name` (e.g. `from src.database import SmartCartDB`), never with relative imports.

## Backend architecture (`src/`)

Data flows in one direction through distinct stages — when changing behavior, know which stage owns it:

1. **Scraping** (`src/scrapers/scraper_coto.py`, `scraper_dia.py`, `scraper_carrefour.py`) — hit each retailer's internal API directly (Coto: internal BFF REST endpoint; Día and Carrefour: VTEX GraphQL `productSearchV3`), paginating per category. Each scraper iterates the category keys its store contributes to `src/shelves.py` (stage 1b) — the live catalog is narrow and deliberately the *same* narrow set in all three stores. `src/scrapers/{coto,dia,carrefour}_categories.json` are static dumps of each store's full category taxonomy (id/slug → `"Top -> Sub -> Leaf"` path string), loaded by `src/taxonomy.py`. They are **not** persisted with the product any more: their two consumers are the dietary parser (the path is evidence text, see stage 2) and `tests/test_shelves.py`, which uses them to prove every key in `SHELVES` actually exists in its store's taxonomy — a typo there scrapes zero products and leaves the shelf silently empty. Día's and Carrefour's requests use a VTEX *persisted query* (fixed `sha256Hash`), so their returned field set is locked server-side — you cannot ask for new fields without a new hash; read anything beyond the known fields defensively with `.get()`. **Coto's price fields can be `null` with the key present**, so `float(d.get("formatPrice", 0))` never reaches its default and raises `TypeError` — read them through `_as_price()`. This surfaced only once the catalog widened past 5 categories, and it failed in the worst available way: the page loop's `except` swallowed it and `break`ed, so the category ended early with whatever it had and `_run_store` counted it **OK**. That sets `StoreRunResult.complete = True`, which is the sole gate on pruning — everything the truncated sweep never reached looks discontinued and gets deleted. **All three page loops now follow one rule: `break` only on a valid, empty page; every other early exit raises `CategoryScrapeError`** (`src/scrapers/errors.py`). Losing the category is strictly better than deleting live catalog, and `_run_store` already tolerates a failed category — which, since pruning became per-category (stage 2), no longer costs the rest of the store its prune. The rule exists because the legit end-of-category and four distinct failures all shared the same `break`, and `_run_store` cannot tell them apart: a non-200 response, a transport exception, a page that repeats already-seen SKUs (the endpoint stopped honoring `page`/`from`, so what's missing is unknowable), and exhausting `MAX_PAGES` (the empty-page cut never arrived). `scrape_category_slice` in Día and Carrefour used to `return None` on error, which the caller read as end-of-category — the exact shape of the `formatPrice: null` bug, one level up. `tests/test_scraper_truncation.py` walks each of those paths per store. Coto's product URL must be built by `build_coto_url()`, not by concatenating the API's `url` field (that field is a relative fragment with no leading slash, which is what produced the broken `https://www.cotodigital.com.ar_/R-...` links). **The slug is built from the product NAME, which is free text, so it goes through `_slugify()`** — a raw `%` (`"La Serenisima 100% Vegetal"`) is an invalid percent-escape and the CDN answers **400 Bad Request** before routing. Measured: 1.954 of 8.143 stored Coto URLs (24%) were broken, and this is the most visible surface there is, because `/optimize`'s breakdown opens one tab per Coto product (Coto has no cart-by-URL, unlike the VTEX pair). Sanitizing beats percent-encoding because the slug resolves nothing — the `R-` code does — and `_slugify` is **idempotent over its own output**, which is what let `src/scripts/repair_coto_urls.py` fix the stored rows without a re-scrape. `tests/test_coto_url.py`'s fixtures used to be pure ASCII alphanumerics, which is exactly why the suite was blind to this entire class.

   **`in_stock` for Día and Carrefour comes from `read_availability()` (`src/scrapers/vtex.py`), and its default is the load-bearing part.** It used to be a literal `True` in both scrapers. Measured against the live endpoint: with the parameters the project sends today (`hideUnavailableItems: True` + `skusFilter: "ALL_AVAILABLE"`) VTEX filters sold-out items server-side and everything returned carries `AvailableQuantity: 10000` — so that `True` was true by construction, not a lie. It is read anyway because of the trap it left armed: with `hideUnavailableItems: False` the same category returns 50 products of which **14 have `AvailableQuantity: 0`**, and loosening that filter is a one-word change. The default when the field is absent is `True`, not `False`: the `sha256Hash` freezes the field set server-side, so a rotated hash that drops the field would otherwise mark the entire catalog as sold out and the optimizer would build no cart at all. **None of this covers per-address availability** — the request sends no `regionId` or segment, so a product can read available here and Día's checkout still answer *"no tiene inventario para tu dirección"*. That is an open TODO item, not something this helper can see; the UI says so in `StoreBreakdownCard`.

   **Carrefour specifics** — same VTEX platform as Día and the same `sha256Hash`, but three things are deliberately *not* copied from `scraper_dia.py`. (a) The request is a **POST with the JSON in the body** to `https://www.carrefour.com.ar/_v/segment/graphql/v1?workspace=master`, which avoids Base64-encoding the variables into a GET URL. (b) `map` is **derived** from the slug's segment count (`",".join(["c"] * len(parts))`) — the MVP mixes 2- and 3-level categories, and Día's hardcoded `"c,c"` sends fewer `c`s than `selectedFacets` on its own 3-level slugs. Relevered against the live Día endpoint on three 3-level slugs, `"c,c"` and `"c,c,c"` return **byte-identical results** (same `recordsFiltered`, same products) — VTEX resolves the filter from `selectedFacets` and the short `map` is not silently widening the result set. Deriving it is still the correct form, but Día's version is not a live bug to chase. (c) Carrefour's `link` field is **relative** (`/producto-123/p`), so `build_carrefour_url()` prefixes the domain — storing it raw reproduces the exact Coto bug above. One failure mode is unique enough to guard explicitly: a rotated persisted-query hash answers **HTTP 200 with an `errors` array and no `data`**, which the "empty page = end of category" pagination rule reads as success, closing the run with 0 products and no error in sight. `extract_search_payload()` (now in `src/scrapers/vtex.py`, shared with Día, which had no such check at all) separates the two — and it **raises** rather than returning `None`, because detecting the rotated hash and then still `break`ing was only half the fix. The taxonomy dump is regenerated with `python -m src.scrapers.get_carrefour_categories` (public VTEX endpoint `/api/catalog_system/pub/category/tree/3`).

1b. **Which shelves get scraped** (`src/shelves.py`) — one table, `SHELVES`, mapping 20 canonical shelf slugs to the per-store category keys (`catv…` id for Coto, URL slug for Día and Carrefour). The three `MVP_CATEGORIES` are `keys_for_store("coto"|"dia"|"carrefour")` over it, so a shelf is added once, for all three stores, in one row.

   **The table exists because alignment is the whole point.** Unification is by EAN (`unified_id = f"prod_{ean}"`), so a product is only comparable across stores if all three swept *the same shelf* — barrelling through more categories per store adds catalog but not comparisons. Three independent lists satisfied that by coincidence and drifted silently: nothing fails when Coto sweeps yerba and Día doesn't, the optimizer simply runs out of things to compare. Selection favours **branded packaged goods**, which is where EANs actually coincide; loose produce, the butcher counter and sliced deli use per-store internal codes and never unify.

   Each store maps to a **tuple** of keys, not one key, because the three taxonomies nest at different depths: Coto only exposes very fine level-3 leaves ("Papas Fritas", "Mani") while Día and Carrefour have level-2 nodes that already cover the shelf (`almacen/snacks`). Current totals: **49 shelves** over 100 Coto keys, 77 Día, 57 Carrefour, across five sections (Congelados joined the original four). The first 20 were the MVP; the second tranche completes the food sections of all three chains. Fresh produce, the butcher counter, fresh fish and in-store bakery stay out permanently — sold by weight under per-store internal codes, no EAN, so they never unify.

   **Two rules about the keys themselves, both learned from silent holes found in production data.** (a) **No key may be an ancestor of another key of the same store.** Carrefour's `mermeladas-y-miel` used the level-2 `desayuno-y-merienda/mermeladas-y-otros-dulces`, which *contains* the `dulce-de-leche` key; both got swept, but the parent's batch carries the child's products too and `save_store_products`' `ON CONFLICT` rewrites `shelf` and `source_category`, so the last shelf swept wins. Nothing is lost — the 27 dulces de leche were filed under `mermeladas-y-miel` and the `dulce-de-leche` shelf read empty for Carrefour — which is exactly why no count and no test caught it: 21/21 categories OK, every night. `tests/test_shelves.py::test_ninguna_clave_contiene_a_otra` now forbids it; the fix is to use the sibling leaves, which partition the parent exactly (23+27+109+16 = 175). (b) **A key existing in the taxonomy dump does not mean it still holds products.** Día renamed `almacen/pastas-y-arroce` to `pastas-y-arroces` and *kept the old node in the tree* with zero products, and merged `almacen/pastas-seca` into it; both keys stayed valid for `test_shelves.py`, which only checks the dump, so `pastas-secas` and `arroz-y-legumbres` were empty for Día for weeks with 24/24 categories reported OK. That is what the empty-category signal in stage 10 exists to catch. Related: `frescos/lacteos/yogures-enteros` and `yogures-descremados` return **byte-identical** results (VTEX does not filter on that leaf), so keeping both meant the second overwrote the first's `source_category` and 108 products were fetched twice a night — one key kept.

   **The taxonomy dumps go stale, and regenerating them has its own trap.** `get_dia_categories.py` derived the slug by `replace()`-ing a hardcoded storefront domain out of the URL; VTEX now returns Día's internal `diaio.myvtex.com` instead, so the replace matched nothing and every key would have been written as a full URL. That does not fail loudly — it writes 569 unusable keys and `test_shelves.py` starts rejecting *every* Día key at once. It parses the URL path now (`slug_from_url`), which is domain-agnostic.

   **One row carries everything, and that is the point.** A `Shelf` is `slug` + `label` + `section` + the per-store keys, so the same row decides what gets scraped, what category a product has (`unified_products.shelf` stores the slug), what can substitute what, and what the mega-menu draws. `STORE_IDS` lives here too, mapping `"coto"` to the `coto_online` that `store_products` and the optimizer use, so adding a store stays one edit on the backend.

   **The canonical slug is what makes cross-store comparison usable.** Each chain names the same shelf differently — yerba is `Mate` at Coto, `Yerba mate` at Día, `Yerba` at Carrefour — so comparing store vocabulary left a product with no possible substitute and nothing said so. Measured before the slug existed, only **7 of the 20** shelves overlapped across all three store pairs; now every shelf covers all three by construction (49/49, enforced by `tests/test_shelves.py`), and "same shelf" is a plain equality instead of an array overlap over per-store taxonomy paths. `shelf_for_key()` returns `None` for a key **outside** the table and `save_store_products()` then rejects the product rather than inventing a shelf — the scrapers only ever iterate `keys_for_store()`, so that can only come from a scraper's standalone `__main__`.

   `SECTIONS` (Almacén / Frescos / Desayuno y merienda / Bebidas) is presentation only: it groups the shelves for the two-level mega-menu and nothing in the backend depends on it. A shelf in an unlisted section still works — it just sorts last and draws the generic icon.

2. **Normalization + persistence** (`src/database.py`, `SmartCartDB`) — `save_store_products()` computes `unified_id = f"prod_{ean}"` and upserts into two tables: `unified_products` (one row per EAN, cross-store) and `store_products` (one row per store's offer, `ON CONFLICT` keyed on `(store_id, store_sku)`). Raw per-store promo payloads are normalized here via `src/promotion_parser.py`'s `PromoTransformer` (`.coto()` / `.dia()` / `.carrefour()`, the last two sharing `_vtex()`) into one of four standard promo `type`s consumed later by the flattener: `direct_discount`, `conditional_discount_flat`, `conditional_discount` (e.g. "2nd unit 50% off"), `multi_buy` (e.g. 3x2). The product's category is the canonical shelf slug the scraper resolved from `src/shelves.py` (stage 1b), stored in `unified_products.shelf`; it is what `GET /category/{slug}` filters on and what gates substitution. `shelf` and `source_category` are read with `prod['...']`, **not** `.get()`: both used to be optional, and a scraper that stopped sending one wrote `NULL` in silence. For `source_category` that means every later partial sweep prunes **zero** rows while reporting `deleted: 0, skipped: False` — a `NULL` never satisfies `source_category = ANY(...)`, so it is indistinguishable from "nothing was delisted". For `shelf` it means the product vanishes from `GET /category` and can never be anyone's substitute. `tests/test_scraper_ingest_keys.py` asserts both keys one step earlier, on each scraper's real output.

   **`src/schema.py` owns the DDL.** There are still no versioned migrations, but the whole schema is one idempotent, declarative module — `CREATE TABLE IF NOT EXISTS` for the three tables, `ADD COLUMN IF NOT EXISTS` for everything added later, `CREATE INDEX IF NOT EXISTS` — applied by `SmartCartDB._ensure_schema()`, `EmbeddingPipeline`, `ScraperTelemetry` and `api.py`'s `lifespan` (that last one is new: `api.py` opens its connections by hand and used to never ensure anything, so a backend on a virgin DB answered `UndefinedColumn` instead of repairing itself; it logs and continues on failure, since a read-only role must still be able to serve). It replaced DDL scattered across three files that between them never created `unified_products` or `store_products` at all: the base schema had been built by hand against the dev database and **existed nowhere in the repo**, so a fresh clone could not boot and column defaults were undiscoverable from source. That is exactly how `units_per_pack DEFAULT 1` came to assert "not a pack" over 287 products that were, with nothing in the code to reveal it. **`ensure_schema` never drops anything** — destructive changes live in `src/scripts/migrate_shelves.py`, run by hand once; `tests/test_schema.py` asserts both the idempotence and the absence of any `DROP`.

   **`unit_type` holds only `'g'`, `'ml'` or `'un'` — that invariant is load-bearing.** Every consumer that compares sizes (the swap heuristic's weight band, `api.py`'s proportional suggestions) pairs identical units or `g`↔`ml` and nothing else, so a row escaping that vocabulary doesn't throw or compute a wrong number — it just stops matching anything and drops out of both features silently. Two paths used to leak: Coto's price-derived fallback for weighables (`"Tomate x Kg"`) emitted `'kg'` uncoverted, and Día's and Carrefour's equivalent fallback passed VTEX's raw `UnidaddeMedida` property straight through (`'gr'`, `'kg'`, whatever the store wrote) whenever it wasn't litres or kilos. All three now end in `size_parser.normalize_magnitude()`, which converts the value and canonicalizes the label, mapping anything unrecognized to `(1.0, 'un')`.

   **The EAN goes through `src/ean.py`'s `normalize_ean()` in all three scrapers, and its two rules pull in opposite directions on purpose.** `unified_products.ean` is `VARCHAR(13)` and `unified_id` is derived from it, so an oversized code is not a cosmetic problem: `save_store_products` runs the category in one transaction, so five Coto rows carrying a 14-digit code reverted the other 75 and left the `catv00003603` shelf ("Gomitas y Gelatinas") empty in the database while the nightly run reported PARTIAL for three nights running — `StringDataRightTruncation` naming a column, not a product. What Coto publishes there is the **GTIN-14 of the case** (packaging indicator + the item's 12 base digits + its own check digit), so a valid one is converted to the GTIN-13 it contains — the standard GS1 derivation, applied **only when the 14's check digit validates**, which is what separates it from guessing. Storing the 14 raw by widening the column would be worse than the crash: it would sit beside the same product's EAN-13 from another chain and never unify, the silent-duplicate failure `unified_product_id` already taught. Anything else over 13 characters becomes `None`, and the product still lands under `f"{store_id}_{store_sku}"` — not unifying forfeits a comparison, unifying wrong breaks the promise.

   The opposite rule is the one that is easy to "improve" into a disaster: **a code of 13 characters or fewer is returned untouched, with nothing validated**. The catalog holds 163 EAN-8, 105 of 11 digits and 281 of 12 — UPCs whose leading zeros all three chains strip identically (measured: not one collides with an existing EAN-13 when zero-padded, and the same short lengths appear in Coto and Carrefour, so they unify with each other today). Running check digits over those would re-key hundreds of products, and the orphan sweep would delete the rows they came from the same night. The VTEX scrapers passed `first_item.get("ean")` through raw — not even a `str()` — so they route through the same helper: the field set is locked by the persisted-query hash, its contents are not.

   Keep the two concerns separate when touching those fallbacks: the `< 1.0` branches in the VTEX scrapers decide the **magnitude** (a sub-1 quotient means `PrecioPorUnd` was per litre/kilo, not per ml/gram) and are a guess about VTEX semantics that shouldn't be changed without fresh data; `normalize_magnitude()` only decides the **vocabulary** and is idempotent over the branches' output.

   **Obsolete rows are pruned per store, scoped to the categories that finished.** `save_store_products()` only upserts, so a delisted product used to keep its `in_stock = TRUE` row forever and stay quotable — the optimizer could build an entire split around something you can't buy. `prune_missing_store_products(store_id, seen_skus, categories=…)` deletes that store's rows whose SKU wasn't seen, then drops `unified_products` left with no offers at all.

   The safety invariant is that `seen_skus` must be the **complete** universe of what the store offers — a partial sweep makes everything it didn't reach look discontinued. **That invariant also holds per category**, which is what `categories` exploits: each row records the category key it was scraped under (`store_products.source_category`, written by all three scrapers and refreshed on every upsert), and the DELETE is restricted to the keys whose sweep closed cleanly (`StoreRunResult.ok_categories`). A failed category no longer costs the rest of the store its prune. That mattered because the gate used to be `StoreRunResult.complete` (zero failed categories): with 5 categories per store a clean night was likely, with 30 it isn't, and one failure left the store un-pruned forever — accumulating `in_stock = TRUE` rows for products that no longer exist. Nothing is loosened in exchange; the failed categories are simply outside the DELETE. Do **not** "simplify" this back to a percentage tolerance on `complete` — that deletes live catalog in proportion to what failed, which is the same damage the truncation bug caused, just smaller. `complete` survives for telemetry and the run summary; it is no longer the prune gate.

   **The scope is only applied when the sweep was partial** (`StoreRunResult.prune_scope`): a complete sweep prunes the whole store, exactly as before. Scoping it anyway would be worse, not safer — rows whose `source_category` is NULL (written before the column existed, or belonging to a category that left `src/shelves.py`) never enter a scoped prune, and no future sweep will rewrite them precisely because they're no longer offered. Measured after one complete Carrefour sweep: 138 rows in that state, which the old whole-store prune would have deleted and a permanently-scoped one never would. Two brakes, sized by the asymmetry between the two errors (a stale row is annoying, an emptied catalog is broken): an empty `seen_skus` never prunes — that's the rotated-persisted-query failure mode above, which reads as a clean run with zero products — and a delete that would take more than `MAX_PRUNE_RATIO` (30%) aborts loudly. **That ratio's denominator is counted inside the same scope**, and it has to be: measured against the whole store, a broken category worth 3% of the catalog would never trip a 30% brake — which is precisely the case the brake exists to catch. `--prune-dry-run` runs the real DELETEs and rolls back, so its reported counts are the actual ones rather than a second query that can drift from the first.

   **Every derived column must appear in the `ON CONFLICT DO UPDATE SET` list.** With no migrations, a re-scrape is the *only* mechanism for correcting bad data — so a column left out of that list is frozen at whatever the first `INSERT` wrote and can never be repaired without dropping the table. The list currently covers `store_item_id`, `source_category`, `name`, `unified_product_id` and the dietary flags alongside the price/stock fields; `unit_type` was omitted while its inseparable partner `total_volume_weight` was updated, which produced two failure modes worth recognizing: rows whose weight had been refreshed but whose unit still came from an older name (`"Fritolim 120 g"` stored as `'ml'`), and every product the size parser failed on staying pinned to `'un'` forever, making any later parser fix a no-op. Both are fixed, but the general rule is the point — when adding a derived column, add it to the update list in the same edit. **`unified_product_id` is the sharpest instance of that rule**, because it is derived from the EAN and its omission is invisible: a store that corrects a wrong EAN on an existing SKU left the offer bolted to the old unified product forever, so that product silently stopped unifying across chains, while the newly-inserted `prod_{new_ean}` row had no offers and the orphan sweep deleted it the same night — a hole that re-opened on every run and showed up in no count and no log.

   **`store_products.name` is the store's own name for that offer, and it is not a duplicate of `unified_products.name`.** The unified name is per-EAN and is overwritten by whichever chain wrote last (`name = EXCLUDED.name`), so of a product's three names the database kept one and did not say which: `prod_77969071` reads `"Chicles Beldent Menta Refrescante 6 Ud."` (Día's) while Coto calls the same EAN `"Chicles BELDENT Menta 20g"`. That is not denormalization — the store's name depends on `(store_id, store_sku)`, not on the EAN, so `store_products` is where it belongs; what was anomalous is three facts sharing one column with two of them discarded. Nothing reads it yet: no endpoint's response changed, the three `JOIN store_products` queries in `api.py` already qualify theirs as `u.name`/`p.name`, and it exists so that hand-verifying what each chain actually returned is possible at all. Rows written before the column stay `NULL` until their next sweep rewrites them.

   **Carrefour's price gap is a member price, not a discount** — `.dia()` turns any `Price < ListPrice` into an unconditional `direct_discount`, and that rule is wrong for Carrefour: its `discountHighlights` name the gap outright (`"PROMO-Mi CRF -mfl-1-6-Dto de 6% Doble Precio"`), i.e. it's the Mi Carrefour loyalty price, and `teasers` separately advertise a `"Tarjeta Carrefour 15%"` that `Price` does *not* reflect. So `.carrefour()` scans both lists for card/loyalty wording and, when it matches, emits the discount with `requires_membership: "mi_carrefour"` — the optimizer then quotes list price by default and only unlocks the lower one for a user who declared that membership (the option exists in `ProfileDrawer`'s `MEMBERSHIP_OPTIONS`). 81 of 427 scraped rows are gated this way and none are unconditional, so treating them as open would have understated Carrefour on nearly every promoted product and won it splits that cost more at the register. Same asymmetry as the dietary flags: quoting too high only forfeits a saving, quoting too low breaks the promise the app is built on.

   **The shelf is the aisle guard (`unified_products.shelf`).** It replaced two columns that described the same fact worse. `category` mapped *leaf* labels through a 12-key dict into 4 buckets, so 5.140 of 6.401 products (80%) landed in `Otros`, putting mayonnaise and meat seasoning in the same bucket and leaving `GET /category/{name}` covering a sliver of the catalog. `tags TEXT[]` held the full slugified taxonomy path and was compared with Postgres overlap (`&&`, GIN-indexed) over the non-top-level segments — correct, but per-EAN: a product sold by all three chains kept whichever store wrote last, so it carried one store's vocabulary. Both are gone. `shelf` is a single slug, identical across chains by construction, compared by equality on a btree index; the 20 shelves cover 6.401 of 6.401 products with exactly one slug each, which is also what let the migration backfill the column out of `tags` without re-scraping anything.

   **Dietary flags** — `src/dietary_parser.py` populates `is_gluten_free`/`is_vegan` from explicit phrases only. `FALSE` means "no evidence", *not* "contains gluten"; never infer these from category, and don't match the bare tokens `gluten` or `vegetal` (they'd fire on "contiene gluten" and "Sémola Vegetales"). Two rules exist because both were violated once and produced real bad data: (1) **only pass text describing that specific product** — name, brand, category path, and store-assigned structured fields (VTEX's `properties`/`clusterHighlights`); marketing `description`/`metaTagDescription` list sibling products in the same line and made a Hellmann's *ketchup* read as vegan, and no phrase rule can fix that since the claim is real but about another product. (2) Flags are **overwritten** on conflict, never `OR`-accumulated — accumulating makes them monotonic, so a false positive can never be corrected even after fixing the parser; a stale `FALSE` is safe, a stale `TRUE` is the one that hurts someone.
3. **Embeddings** (`src/embeddings.py`) — a separate offline pipeline (`EmbeddingPipeline.generate_and_save_embeddings()`) that encodes `"{brand} {name}"` per product with `all-MiniLM-L6-v2` and backfills `unified_products.name_embedding` (pgvector `vector(384)`, HNSW index, cosine ops). Run this after scraping new products, before semantic search will find them.
4. **(retired) Category tree for the mega-menu** — `src/category_tree.py` merged the *complete* Coto and Día taxonomies (Carrefour never made it in) into one 2-3 level tree at API startup, using normalized-text equality, token-subset containment and a conservative 0.90 cosine backstop over the same sentence-transformers model `/search` had loaded. It is deleted. The tree described ~15 top-levels and hundreds of leaves over a catalog of 20 shelves, so nearly every click landed on a node with no products and fell back to `GET /search?q=<label>` — a semantic search for a category name over a catalog that did not contain that category. The mega-menu now draws the shelves themselves (stage 1b), where every leaf has products by construction.

   Its **0.90 threshold discussion survives as precedent**, and other stages still cite it: empirically, genuine near-duplicate category pairs and merely-related sibling categories occupy overlapping similarity bands (a true duplicate pair scored 0.798 while a false-positive-risk sibling pair scored 0.778), so no single threshold separates them, and the fix for a vocabulary mismatch is an explicit table rather than a loosened cutoff. `src/shelves.py` *is* that table.

5. **Coto delivery logistics** (`src/coto_logistics.py`) — an online, per-request lookup (not ingest, hence not under `scrapers/`) that answers two questions before the solver runs: does Coto deliver to these coordinates, and what does shipping cost. It sits between the request and the flatten/CP-SAT stages because it changes two of the solver's inputs (which stores participate, and Coto's `delivery_cost`).

   Endpoint reality, relevered against the live site — **do not trust older notes describing `www.coto.com.ar/getCobertura` or a `getCostoEnvio` POST; neither exists**. The `cotodigital*.com.ar` domains all 301 to `www.coto.com.ar`, an Angular SPA that serves its `index.html` with **HTTP 200 for any unknown path** — so a client that only checks the status code parses a web page as if it were data. That's why `_fetch_json()` requires a JSON content-type. The real route is the ATG actor the SPA itself calls: `GET /rest/model/atg/actors/cProfileActor/getCobertura?lat=&lng=`. It is **public** — no login, no cookie, no `_dynSessConf` token (verified with and without; identical responses), so there is no session handshake to perform. Its payload nests everything one level down: `{"sucursal": {"coberturaCD": 1, "codigoError": "0", "mensajeError": "-", "sucursal": "220"}}`, and the coverage rule (copied from Coto's own frontend) is `sucursal.mensajeError == "-"`.

   **There is no address-level shipping-cost endpoint.** The bundle contains zero occurrences of `costo`/`importe`, and the actors that do price delivery (`getGrillaCupos`, `getCuposHoy`, `getEntregaRapida`) all return `USER_NOT_AUTHENTICATED`: Coto's real shipping cost is a function of a logged-in user's server-side cart and chosen time slot, not of coordinates. What *is* readable anonymously is the published tariff in `getParametros2` → `ENTREGA_RAPIDA_COSTO` (3399 as of Jul 2026), which `get_shipping_cost()` uses. It is one global number, identical for every covered address — that limitation is documented, not hidden, and the UI labels a fallback as an estimate.

   The module is **fail-open** and never raises: on timeout, HTML, or a malformed payload, Coto keeps competing using the frontend's per-zone fallback cost with `source: "fallback"`. Only an affirmative "no coverage" verdict excludes the store — a third party's endpoint hiccuping must not silently delete half the catalog and hand the user a worse price. Correspondingly, `check_coverage()` distinguishes `ok=False` ("couldn't determine") from `covered=False` ("Coto said no"), and **only successful lookups are cached**, so a timeout doesn't pin the fallback for the whole 30-minute TTL.

   Related but deliberately untouched: `getParametros2` also exposes `MINIMOGENERAL = 30000`, against the `15000` hardcoded for `coto_online` in `optimize_cart`'s `DEFAULT_MIN_SPEND_LIMITS`. It was not confirmed that these are the same concept, and changing it flips which carts come back infeasible — treat as an open question, not a bug to fix in passing.
6. **Search & optimization API** (`src/api.py`) — FastAPI app; loads the sentence-transformers model and builds the category tree once at startup (`lifespan`, stored in the `ml_models` dict). Endpoints:
   - `GET /search?q=` — pgvector cosine-distance nearest-neighbor over `name_embedding`, **retrieve-then-rerank in one query**: a `pool` CTE takes the `SEARCH_POOL_SIZE` (100) nearest by pure distance — the only ordering the HNSW index can accelerate — then the outer query reorders that pool by `distance − STORE_BONUS × LEAST(GREATEST(store_count−1,0), STORE_BONUS_CAP)` and cuts to `limit`.

     **The pool must be larger than `limit`, and that is the whole point.** Pure distance gave a product stocked by all three stores no edge over one sold in a single store, which for a price-comparison app leaves results the optimizer can do nothing with at the top. It cannot be fixed client-side: the browser only receives the `limit` rows Postgres already chose, so a 3-store product at rank 25 does not exist for it — reordering there changes the *order* of the top-N but never its *composition*.

     **`hnsw.ef_search` defaults to 40 and is a ceiling on rows the index returns**, so `LIMIT 100` silently yields 40 and the rerank permutes the same 40 candidates forever — the feature looks alive and does nothing. It is raised per connection via `SELECT set_config('hnsw.ef_search', …)`; plain `SET` cannot take a bind parameter. `tests/test_search_ranking.py` asserts the pool comes back at full size, which is what makes that failure loud.

     **`STORE_BONUS = 0.01` is calibrated, not guessed, and must not be raised to "catch more".** Over 15 real catalog queries the natural top-20 spread (d@20 − d@1) has median 0.110, so the cap makes the worst-case relevance loss `STORE_BONUS × STORE_BONUS_CAP` = 0.02, ~18% of it; measured effect is 5% of the top-20 changing and mean store count 1.49 → 1.57. At 0.02 the query `yogur bebible` drops two actually-*bebible* yogurts (d=0.368, 0.370) for three 3-store Yogurísimo *Griego* (d≈0.39) — the embedding does not treat "bebible" as a hard constraint, so a moderate bonus buys availability with literal relevance. At 0.05 a product can climb from rank 79, clearing the entire rank-20→100 relevance gap (0.105). Same discipline as the 0.90 in stage 4: bound it by the damage it must not cause. Band-based ranking (`ORDER BY floor(d/w), …`) was measured too and gives identical numbers at equal conservatism, so the capped linear bonus wins on simplicity.

     `distance` is returned **raw**, never the ranking score — it is semantic relevance, and folding the bonus in would make the field unreadable. `store_count` counts only `in_stock` offers while `available_at_stores` carries them all, so the two can legitimately disagree.
   - `GET /categories` — the shelves grouped by section, straight from `src/shelves.py`. It touches no database: the shelf table *is* the taxonomy, so the menu cannot drift from what gets scraped. It replaced both the old flat 4-bucket list (`SELECT DISTINCT category`, which nothing consumed) and `GET /categories/tree`; `has_direct_category_match` went with them, because every click now routes to `GET /category/{slug}`.
   - `GET /category/{slug}` — the products of one shelf, `WHERE u.shelf = %s`. A slug outside `SHELVES` answers **404, not an empty list**: the table is closed and known, so "no products" and "no such shelf" are different facts and the caller should not have to guess which one it got. It orders by `store_count DESC, name ASC`, which costs nothing because its `distance` is a hardcoded `0.0` — there is no relevance to trade away — and fixes a real defect: the query had **no `ORDER BY` at all**, so `LIMIT 50` returned whichever 50 rows Postgres had at hand and two identical calls could answer with different products.

     **All three product endpoints go through `_build_product_response()`.** `/search` used to build its dict inline and was the only one without `min_price` and `image_url`; that gap stopped being defensible once `unit_price` existed, since search is where the user enters the catalog. The only thing that distinguishes them is `distance`, now a parameter: `/search` passes the **raw** cosine distance (never the ordering score, which would fold in the availability bonus and make the field unreadable) and the other two a fixed `0.0`. Note `min_price` is the minimum of the **list** prices, promos ignored — a fallback, not the price to display.

     **`unit_price` (`{value, base}`) is the price per unit of measure, computed by `_build_unit_price()`.** It divides the price the grid actually announces — the cheapest `promo_unit_price ?? base_price` across offers, the same rule as the frontend's `resolveBestOffer` — by `total_volume_weight`. It was born in the backend because that is where the data is: the frontend only had `min_price` (list prices, promos ignored), so a card showed a discounted price beside a per-kilo figure derived from a different number, and `/search` did not send `min_price` at all, so in search results it simply did not render. **One base, always: per kilo for `'g'`, per litre for `'ml'`.** The old cutoff at 1000 (per 100 g below, per kilo above) existed because a big number on a small package reads as a typo — true, and measured: a single base changes the label on 89% of the catalog and puts 275 products (4,5%) over $100.000/kg, topping out at a 0,375 g saffron showing $9.710.526/kg. It loses anyway, because two bases in one grid break the comparability that is the entire reason to show the number; the median sits at a perfectly legible $14.929/kg. **`substitutions.format_size()` keeps its own cutoff at 1000** (`1000 g` → `"1 Kg"`) and that is not an inconsistency left behind: it writes a *size*, which is read one product at a time, not a *comparison base*, which is read down a column. `None` for `unit_type = 'un'` and for anything outside the vocabulary — `'un'` is what `normalize_magnitude()` returns when it **gave up**, with `total_volume_weight` at the `1.0` placeholder, so a price derived from it is the product's price wearing a measurement nobody took. Multipack weights are **not** multiplied (stage 7 explains why), so that error can only run expensive.

     All three endpoints (`/search`, `/category` and `/products/by-ids`) build their offers through the shared `_build_store_offer()`, which also fills `promo_unit_price`/`promo_description` per offer: the net unit price **at quantity 1**, computed by `src/flattener.py`'s `evaluate_best_promo()` — the same evaluator the optimizer uses, never a reimplementation. Evaluating at `q=1` is what makes the grid's semantics fall out for free: a `direct_discount` applies from the first unit, while the three conditional types are gated behind `q >= required_quantity` and therefore leave `promo_unit_price` at `None` until the user raises the quantity (at which point `POST /price-preview` takes over). It is called with **no memberships**, since the grid is anonymous and a card-gated promo must not be advertised as the default price. `None` also covers the case of a promo whose `discount_price_per_unit` equals `base_price` — real in the current data, and not something to announce.
   - `POST /products/by-ids` — batch lookup of `List[ProductResponse]` by `unified_id`, for the frontend's purchase history (which stores ids in `localStorage` and has to resolve them against *today's* catalog). Neither existing endpoint can do it: `/price-preview` returns prices but no metadata, and `/optimize` can answer 400 on minimum spend.

     **An id absent from the response means exactly one thing: the row no longer exists in `unified_products`, i.e. the pruner deleted it (stage 2).** That contract is the entire reason the endpoint exists, and two rules follow from it that must not be "simplified":
     - **It does not filter by `in_stock`.** If it dropped out-of-stock products, an absent id would mean either "delisted forever" or "sold out today" and the UI could not tell them apart — it would tell the user a product is gone when it comes back tomorrow. That is precisely `/price-preview`'s problem, and why `useUnavailableCartItems.js` has to *not* flag ids missing from it. "Exists but nobody stocks it today" is a real, distinct state (`prune_missing_store_products` only deletes the unified row when **no** offers are left), and it is reported as `store_count == 0`.
     - **It takes no dietary filters.** Any filter that can drop an id breaks the contract above. A lookup by id has no facets — the caller already knows which products it wants.

     Results come back **in the order requested** (restored in Python from the row dict, which also dedupes: a repeated id must not become two rows, since the frontend keys the grid by `unified_id`). `distance` is a hardcoded `0.0`, same as `/category` — no query, no relevance. `MAX_PRODUCTS_BY_IDS = 100` bounds the list, since unlike `/search` there is no natural `limit`; Pydantic's `min_length`/`max_length` enforce it, so both ends are a 422 with no handler code. Unlike `coto_logistics.py` or `analytics.py`, it **does not fail open to `[]`** — a silently empty response is indistinguishable from "every one of your usuals was delisted", the worst possible lie for this feature. The frontend is the layer that fails open (it renders nothing); the API tells the truth.

     `_build_product_response()` and `_fetch_offers_by_product()` were extracted at this point and are shared with `/category`. **`/search` deliberately does not use the first one**: it still sends no `min_price`/`image_url`, and that gap stays a documented gap rather than being changed as a side effect of a refactor.

   - `GET /demo-cart` — a sample cart built from **today's** catalog, for the home page's cold start. Someone opening the public link has to search and pick a dozen products before reaching the only thing that distinguishes SmartCart (the split), and that is exactly the work a tester will not do.

     **The backend picks it, not a list of ids in the frontend**, for two reasons that point the same way: the nightly pruner deletes delisted products, so fixed ids rot on their own with no warning (the button would quietly build a three-product cart), and the catalog is backend data anyway. Three criteria, each from something that went wrong when tried: `store_count = 3` (a product only one chain sells gives the optimizer nothing to decide); the **median**-priced product of each shelf, not the most expensive — the obvious criterion produced a $384.000 liquor cabinet (Amarula, Chandon, Catena) while the median gives milk, pasta, rice and yerba; and one product per shelf over `DEMO_CART_SHELVES`, an explicit list, because what is chosen here is *content* and it has to read like somebody's weekly shop. Quantity is 2 so the conditional promos (3x2, 2nd unit 50%) clear their thresholds and the breakdown actually shows one. Measured: ~$90.000, comfortably over all three minimum-spend thresholds — which matters because a cheap cart comes back **infeasible**, and that would be the first screen. Returns `[]` on an empty database (the frontend then draws no button), which beats a 404: having no catalog is not a bad request. `DemoCartItem` carries the name — `CartItem` is what goes *in* to `/optimize` and has no reason to carry it — so the frontend needs one round trip, not two.
   - `GET /logistics/coto/coverage?lat=&lng=` — thin wrapper over `check_coverage()` so the frontend's address onboarding can warn immediately that Coto doesn't reach an address, instead of the user finding out only after building a cart.
   - `POST /optimize` — the core flow: optional `lat`/`lng` first go through `resolve_coto_logistics()` (stage 5), which may add `coto_online` to `excluded_stores` or overwrite its `delivery_cost`; then `src/flattener.py`'s `flatten_cart_prices()` "flattens" each cart line into its cheapest net cost per store for the requested quantity (evaluating all applicable promos, gated by `user_memberships`), and `src/optimizer.py`'s `optimize_cart()` builds a CP-SAT model (`ortools`) with one boolean var per (product, store) pair plus a per-store "active" var, enforcing each store's minimum-spend threshold as a hard constraint and minimizing total cost (subtotal + delivery − capped bank-card discount). Returns HTTP 400 with a human-readable `detail` when infeasible. The response carries a `logistics.coto` block (`covered`/`sucursal`/`delivery_cost`/`source`/`message`) and `excluded_stores` so the UI can explain a missing store rather than leaving it looking merely expensive.

     **Registering a store is a two-file change, always in the same commit.** `optimize_cart` derives its store list from the keys of `min_spend_limits` (`DEFAULT_MIN_SPEND_LIMITS`) and then indexes `delivery_costs[store]` with **no default**, while the request's `delivery_costs` comes from the frontend's per-zone table. Adding a key to one side only either crashes `/optimize` with a `KeyError` (optimizer knows the store, frontend doesn't send it) or silently benches the store (frontend sends it, optimizer's limits don't list it) — and in that second case, a cart item sold *only* there hits the `sum([]) == 1` trap below and comes back infeasible blaming minimum spend. Carrefour is `carrefour_online`: min spend $20.000, flat $3.500 delivery in all four zones. It used to have **no `bank_promos` entry** because its discounts are day-specific and the model has no notion of day; stage 8's loader now filters to the current weekday before the table ever reaches the solver, so Carrefour participates with no special case. Carrefour has no coverage/tariff endpoint of its own, so unlike Coto it always uses the per-zone cost.

     Excluding a store is **not** the same as making it expensive: `optimize_cart(excluded_stores=[...])` drops it from `stores` entirely. That creates a trap worth knowing — a product sold only by the excluded store loses every one of its boolean vars, turning its assignment constraint into `sum([]) == 1`, which the solver reports as plain infeasible and the API would then blame on minimum-spend ("add more products"), advice that cannot possibly help. `optimize_cart` therefore detects those products *before* building the model and returns `unavailable_products` with a message naming the real cause.

     Post-solve, `_enrich_successful_result()` adds four things that never change the split or the total, each behind `_optional_feature` so one can fail without taking the others: `price_savings` (`_compute_price_savings`), semantic "smart replacement" suggestions (nearest-neighbor by embedding within the same shelf, ≥20% cheaper for equal weight), `strategic_swaps` (stage 7), and — for VTEX stores in the split — a "magic link" checkout URL (`generate_vtex_magic_link`).

     **`price_savings` is a per-line comparison, not a baseline, and the difference is the whole point.** For each line of the split it takes the **most expensive** store that carries that product minus what is actually paid. Shipping and the bank discount are outside it, so the number is **not comparable against `total_spent_net`** nor against any difference of totals — `SavingsPanel` says so in the copy and the docstring says so in the code, because it is the kind of figure someone will inevitably try to reconcile. Excluded stores are dropped from the `max()`: a store that can't deliver would inflate the saving with a purchase the user could not have made. Lines that yield zero (a product sold by a single store) are left out of `items` rather than listed at 0.

     There is **no** single-store baseline anywhere: `optimize_cart` is never re-run to price "the whole cart at Coto", so the response cannot answer "was splitting worth it?" — that gap is a live TODO item, not an omission from this document.
7. **Store-closure heuristic** (`src/strategic_swaps.py`) — post-solve, answers a question the solver structurally cannot: *should a whole store be dropped by substituting the products only it carries?* CP-SAT is optimal, but over a space where cart products are immutable, so five Carrefour-exclusive items force `y[carrefour] = 1`, and an open store drags its $20.000 minimum plus a second delivery. `find_strategic_swaps()` finds each active store's **anchors** (products with no offer in any other non-excluded store), pulls same-aisle semantic replacements, and re-runs the solver on the substituted cart with that store excluded. Result lands in `strategic_swaps` on the `/optimize` response (always present on `success`; `[]` is the normal case).

   Four rules, each load-bearing. (a) **The what-if calls `optimize_cart()`, it does not recompute cost** — hand-rolling "subtotal + delivery − bank discount" would mean another copy of the `bank_promos` table and a second arithmetic beside the model's integer cents with its truncating division; a saving computed differently from the total already shown to the user is a guaranteed silent bug. `optimize_cart` grew an optional `flat_prices=` for this (pass it **filtered to that cart's UIDs** — `products` comes from its keys, so a stray UID becomes a phantom with its own `== 1` constraint). (b) **A store with zero anchors is skipped without a single query** — closing it was already a feasible point the optimal solver evaluated and rejected, so the simulation cannot win; the heuristic only adds value where substitution leaves the solver's search space. Note this is a test on *anchors*, not on how many stores are in the split: a **single-store split must still be analysed**, and is in fact the worst case. One cheap exclusive product forces its store open, that store's minimum then drags the entire rest of the cart in behind it, and the split collapses to one store — the real report that caught this was a $1.550 Carrefour-only vinegar pulling 15 alfajores in at $2.125 to clear the $20.000 minimum when Coto had them at $1.062,50 on promo ($36.925 vs $15.750). An early `len(split) < 2` guard read that shape as "nothing to close" and suppressed the alert on exactly the carts that needed it most. (c) Anchors are computed against **non-excluded** stores, not *active* ones: closing a store lets the solver switch on one that was off, so a product that store also carries relocates by itself and needs no swap. (d) Replacements are **strict** — same shelf (`u.shelf = %s`), compatible unit, and weight within 0.5x–2x — because without a size band the heuristic "saves" money by shrinking the cart; comparability gates the candidate, but the simulation prices the **real** cost, never a weight-prorated one. It is all-or-nothing per store (one unreplaceable anchor kills the closure), fail-open like `coto_logistics.py`, and lives behind its own `_optional_feature` in `api.py` so a failure here can't take down `price_savings` and `suggestions` the way a surrounding broad `except` would.

   Two constraints on candidate selection exist because violating them corrupts the simulation silently: a candidate **already in the cart** and two anchors sharing **one** replacement both produce a duplicated `unified_id`, and `flatten_cart_prices` resolves quantity with the last occurrence while `optimize_cart` uses the first — the simulated cost would correspond to no real cart. Candidates are also priced at the **anchor's quantity**, grouped into one flatten call per distinct quantity, since conditional promos (3x2, 2nd unit 50%) only unlock above a threshold.

   **Multipacks are compared, never multiplied.** `extract_pack_count()` gates candidates so a six-pack is only ever swapped for another six-pack. It deliberately does *not* multiply the weight, and that is not laziness: relieved against the real catalog, the number next to the `xN` is sometimes the pack total (`"X6 ALFA PAMPA 360g"`, `"x6 244 grs"`) and sometimes the per-unit size (`"Entre Dos x6 45 g."`, `"Chocoarroz x6 36 grs"`), with nothing in the name to tell them apart. Multiplying would inflate exactly the rows that already carried the total, and an inflated weight *lowers* price-per-gram — the product would look like a bargain and get recommended. Same asymmetry the dietary flags follow: erring expensive forfeits a saving, erring cheap breaks the promise. `_build_unit_price()` in stage 6 does not multiply either, and lands on the same side for the same reason: when the stored size was per-unit its price-per-kilo comes out N× **too high**, never too low.

   Both this and `api.py`'s suggestions rely on `unit_type` holding only `'g'`/`'ml'`/`'un'` — see the unit-vocabulary invariant in stage 2.

   **The store-vocabulary gap is closed by construction.** "Same aisle" is `u.shelf = %s`, and the shelf slug is written identically by all three scrapers (stage 1b), so a product's substitutes are exactly the products on its shelf in any store. A product with **no** shelf gets no candidates at all — `fetch_candidates` returns early — which is the safe direction, the same asymmetry as everywhere else: a missed swap forfeits a saving, a swap from another aisle breaks the promise the app is built on.

   The problem this replaced is worth remembering, because any *new* per-store attribute will hit it. Comparison used to run over `tags`, each store's own taxonomy path, with Postgres overlap (`&&`): Carrefour files vinegar under `almacen → aceites-y-vinagres` and Día under `almacen → aceites-y-aderezos`, which do not overlap, so a Carrefour vinegar could never be matched against the Día vinegar that is its closest embedding neighbour (measured: `Vinagre de Vino DIA 500 Ml.` at distance 0.350 from the Carrefour Bulnez, nearer than any candidate the filter did admit). The fix was never to loosen `&&` into a similarity threshold — see the 0.90 discussion in stage 4 — but an explicit alias table, which is what `src/shelves.py` is.

8. **Bank discounts** (`src/promotions/`, `src/bank_promos.py`) — an offline pipeline, unrelated to stage 1's catalog scraping: it relieves the **card/wallet discounts each chain publishes for the whole store**, which hang off no product and land in a JSON file, not Postgres. It exists because `optimize_cart` used to hardcode a two-row table (Galicia 20% at Coto, Macro 15% at Día) that was stale and had no notion of day.

   `DiscountScraper` (ABC) is a template method: `scrape()` fixes the whole lifecycle (fetch → iterate → translate → validate → dedupe → report) and is **not** overridden; subclasses supply only `_fetch_raw`/`_iter_raw_promos`/`_to_discount`. Discarding is centralized there on purpose — it's the part of scraping that breaks silently, and three subclasses filtering on their own would mean three criteria and no count of what was thrown away (`self.discards` is a Counter the runner prints). All three emit the same frozen `BankDiscount` dataclass, which validates in `__post_init__`; an invalid record is dropped with a log, never repaired.

   **The transport is deliberately not uniform.** `CotoScraper` uses `httpx` against `getPromocionesMulticanal`, a public ATG actor — verified with a valid `_dynSessConf`, a bogus one, and none at all: byte-identical responses, so **the token is not hardcoded** (same finding as stage 5). Día and Carrefour render their grids client-side with no JSON equivalent, so they subclass `PlaywrightScraper`, which owns the browser lifecycle and **imports playwright lazily inside the method** — that's what keeps `CotoScraper` and the API working on a machine with no Chromium.

   Per-store specifics worth knowing: Coto's bank name is in **no field** (`banco` is a numeric code reused across unrelated promos), so identity comes from the logo filename (`logo_naranjax2.png`) — which is why `banks.py`'s alias boundary blocks letters but **allows digits**, since a `\b` would reject every versioned icon. Día's days come from **clicking the day tabs** and recording which cards appear, not from parsing prose, and its "Ver Legales" is a real modal that captures pointer events — leaving it open breaks every subsequent card, hence open→read→close. Carrefour needs no clicking (the legal is already in the DOM, just collapsed) but has two traps: its big number is the **installment count** on financing cards ("6" in "Hasta 6 Cuotas"), so financing is filtered *before* reading it, and only cards carrying the `logoOnline` icon apply to web purchases (13 of 32 are store-only).

   `legal_parser.py` is pure and holds the rules that were each learned from a real text: caps are read only when a tope word precedes the amount, **worked examples are stripped first** (Columbia's "EJEMPLO: ... REINTEGRO DE $200" made the min-rule report a $200 cap instead of $10.000), ties take the **lower** cap, and `parse_money_ars` reads `.` as a thousands separator — the opposite of `coto_logistics.parse_amount`, whose back-office rule turns `$12.000` into 12. Percentages have a `strict` mode for long legals so financing rates ("CFT 0%", "T.N.A. 0,00%") can't pass as discounts.

   **The loader filters by weekday, and that's the load-bearing part.** CP-SAT has no notion of day, so `load_bank_promos(today)` emits only what's valid now — which is what let Carrefour into the table at all (see stage 6). It also **sorts by descending percentage**, because `optimize_cart` picks the *first* matching card, not the best, and real data has three Naranja X tiers at Coto. It is fail-open: a missing or corrupt file returns `FALLBACK_BANK_PROMOS` (the old hardcoded table, now the single source both the optimizer and `test_optimizer_correctness.py` import, so the two copies can no longer drift). An empty day legitimately returns `{}` — falling back there would invent a discount that isn't running.

   **Adding an entity is a two-file change, and `tests/test_promos.py` now enforces it.** `banks.py`'s slugs must exist in `ProfileDrawer.jsx`'s `CARD_OPTIONS`/`MEMBERSHIP_OPTIONS`, since `optimize_cart` compares by exact equality — a scraped bank the UI doesn't offer can never be activated, silently, every night. Those constants are now `{value, label}` pairs: the `value` is what travels to `/optimize`, the `label` is only drawn, and the parity tests check both directions plus that every label equals `display_name(value)` — the backend writes the entity's name into the promo description (`"21% Off con Mi Carrefour"`, via `promotion_parser.py`), so two spellings would show the same entity twice on one screen. Making it verifiable immediately turned up four banks the scraper emits and the UI never offered (Provincia, HSBC, Itaú, Hipotecario) and one membership for a chain the project doesn't cover (`jumbo_mas`). `MEMBERSHIP_ENTITIES` decides which of the two lists a slug belongs to (`is_membership` on the promo), because loyalty programs like Comunidad Coto travel in `user_memberships`, not `user_cards`.

9. **Analytics emitter** (`src/analytics.py`) — fires one `cart_optimized` event per optimization at **SmartCart Performance Analyzer** (`../SmartCart Performance Analyzer`), a separate service with its own Postgres warehouse on `:5433` and ingest API on `:8001` that feeds Power BI. The contract lives over there (`src/models.py`, rejects violations with 422) and is nearly 1:1 with what `optimize_cart()` already returns — `status`, `total_spent_net`, `split` and `excluded_stores` have the same names and shapes — so `build_cart_optimized_event()` forwards and computes nothing. The aggregates are the analyzer's job (`repository.py` there); recomputing them here would be a second definition that drifts silently.

   **The overriding invariant is that analytics can neither break nor slow `/optimize`.** Everything with I/O runs in a `BackgroundTask` with a 2s timeout inside a `try/except` that only logs — fail-open, same as `coto_logistics.py`. Two rules fall out of it and both are load-bearing:

   **`BackgroundTasks` does not survive a `raise HTTPException`.** FastAPI attaches the tasks to the response *after* the endpoint returns (`fastapi/routing.py`, `if raw_response.background is None`); if it raises, the exception handler builds a different response with `background=None` and the task never runs. That's why `optimize_shopping_cart`'s infeasible branch **returns `JSONResponse(status_code=400, content={"detail": msg})` instead of raising** — byte-identical on the wire to what the default handler produced, so `optimize.js`'s 400 branch is unaffected. "Cleaning this up" back to a `raise` silently drops every infeasible event, which is exactly the friction KPI (`% carritos inviables`) the integration exists to measure. Both exits emit; the `HTTPException(500)` from an engine failure deliberately does not.

   **Config comes from a `.env`, never from the shell.** `load_dotenv()` runs at import (it does not override already-exported vars, so a manual `$env:` still wins). The reason is specific: `uvicorn --reload` reloads *code* but never the *environment* — the worker inherits the parent's `os.environ` frozen at launch — so a server started before the variables existed runs the new code and emits nothing. Missing `ANALYTICS_API_KEY` means no emission by design (a dev without the analyzer must not be spammed), which makes a misconfigured server look identical to a healthy one; `analytics_status()` and `check_analyzer_health()` exist only to break that tie, reported once in `lifespan` and exposed in `GET /`. Diagnosing this cost a forensic session once already.

   Note `unavailable_products` and other unknown keys ride along fine: the analyzer's models are `extra="allow"` and keep the whole event in `raw_payload`. The frontend side is one field — `anon_user_id`, a `crypto.randomUUID()` minted and migrated into `smartcart_profile_v1` by an effect in `ProfileContext` (the key is **not** versioned; the effect *is* the migration) — plus `zone`, which travels explicitly because a `delivery_costs` dict can't be mapped back to a zone label.

10. **Orquestación desatendida** (`src/scripts/orchestrator.py`, `src/logging_setup.py`, `src/scraper_telemetry.py`, `ops/oracle/`) — the unattended path around stage 1. It adds **only** operations concerns: the sweep itself stays in `run_scrapers.py`, whose `STORE_RUNNERS` the orchestrator imports. Registering a store there is still one entry.

    **Telemetry rows open before the work, not after.** `ScraperTelemetry.step()` INSERTs the row as `RUNNING` and UPDATEs it on exit, one row per step (`coto`/`dia`/`carrefour`/`embeddings`) keyed by a shared `run_id`. A single INSERT at the end would be simpler and would lose exactly the case worth catching: killed by the watchdog, OOM, reboot. Those leave no row at all, which is indistinguishable from "cron never fired" — whereas a stranded `RUNNING` row says precisely what happened. `start_time` comes from Python, not `now()`, so `duration_seconds` measures the step and not the round-trip. The writer is fail-open on its own connection (same doctrine as `coto_logistics.py` and `analytics.py`): observability must not be able to break what it observes.

    **`status` semantics are load-bearing** — `SUCCESS` needs every category *and* an un-aborted prune; `PARTIAL` is ≥1 category OK with either a failed category, an **empty** category or a `skipped` prune; `FAILED` is zero categories OK. A skipped prune counts as PARTIAL on purpose: both of its brakes (zero SKUs seen, or a delete exceeding `MAX_PRUNE_RATIO`) only fire on the signature of a broken scraper, so a dashboard that paints that green hides the one thing worth looking at.

    **An empty category is PARTIAL, and it is the subtlest of the four.** A category that closes cleanly with zero products is not an error — the store answered, the sweep finished, and pruning inside it is correct because there is nothing to delete — so it used to be a bare `logger.warning` and the category still counted OK. But it is also precisely what a **dead key** looks like (stage 1b: Día renamed a slug and left the old one in the tree), and that shape survived weeks of green runs. `StoreRunResult.empty_categories` records which ones, `scraper_execution_logs.categories_empty` counts them, and the names go into `error_message` because the count alone forces a trip to that night's log to learn what to look at. It deliberately does **not** raise: legitimately empty shelves exist, and failing the store would cost the prune for everything else over one out-of-stock aisle. Same asymmetry as everywhere else — PARTIAL breaks nothing and cannot be ignored.

    **`save_store_products()` now raises instead of swallowing** (it used to `print` the error and return normally). That `except` never saved any data — psycopg3 already wrapped the batch in a transaction, so a mid-batch error had rolled the category back regardless — it only hid the loss: with Postgres down the run reported success with zero rows written, then pruned against a `seen_skus` that never landed. Its return value is now the row count. Side effect accepted: the scrapers' `__main__` blocks abort with a traceback rather than continuing.

    **Logging deliberately avoids `TimedRotatingFileHandler`.** That handler rotates only while the process is alive across midnight; a job that starts at 03:00 and runs for minutes never crosses it, so it would append to one unbounded file forever. For a short daily process the correct rotation is the date in the filename (`logs/orchestrator_YYYYMMDD.log`) plus an explicit retention sweep. A `logging.Filter` stamps the `run_id` on every record — including third-party loggers — so one run is a `grep` and cross-references its telemetry rows.

    **The sweep runs on GitHub Actions against Neon today; the Oracle VM is designed, committed and blocked** (`ops/README.md` holds the status and the exit condition; `ops/oracle/` the runbook). Two deployments described at once is normally rotten documentation — here it is deliberate and dated. Read `ops/README.md` first.

    The path to here matters, because each step was closed by a fact rather than a preference. A cron job under WSL2 never fired, because Windows shuts the VM down on idle and no script fixes that. AWS was designed and abandoned: since 15-Jul-2025 new accounts get credits instead of a 12-month free tier, and both available accounts were empty — ~US$16/month, US$14 of it RDS. Neon + Actions was built, then challenged by Neon's **100 CU-hours/month** ceiling once the goal became real users; storage was never the constraint (**51 MB measured** against 0.5 GB), compute was. Oracle Always Free has no compute-hour cap, which is why it is the target — but it will not hand over the machine: A1 returns *out of capacity* persistently in Santiago, only 1 OCPU / 1 GB was ever granted, and 1 GB does not hold `all-MiniLM-L6-v2` (~1.5 GB, needed by both `/search` and the embeddings step). **Note Oracle halved Always Free A1 on 15-Jun-2026, unannounced: 4 OCPU/24 GB became 2/12.** Any guide older than that promises double.

    **The supermarket endpoints are a gate, and it must be re-passed from every new place the sweep will run.** `ops/probe_endpoints.py` (deliberately importing nothing from `src/`, so it runs on a bare box with just httpx) checks four surfaces — Coto's catalogue BFF, Coto's ATG `getCobertura`, and Día's and Carrefour's `productSearchV3` — and demands JSON content-type *and* the expected shape, never just HTTP 200: Coto's SPA serves its `index.html` with 200 for any unknown path, so status-only checking parses a web page as data. Passed from Argentina and from Oracle/Santiago; the Actions run is the one still pending. Latency from Santiago came in at +120-220 ms, far above the ~30 ms estimated — and it does not matter: the sweep is ~560 requests, so that is under 2 minutes on ~30, because the scrapers' own anti-bot sleeps outweigh the network ten to one.

    **The nightly path contains zero lines of bash on either destination.** On Actions, `workflow_dispatch` takes one free-text `args` input passed through `env` (never interpolated into the `run`, since `${{ }}` is substituted before a shell exists and its contents become code); a typed input per flag would need one conditional each and would restate the flag list `build_arg_parser()` already owns. On the VM, four declarative systemd units carry no conditional at all — `WorkingDirectory`, `EnvironmentFile`, `User` and journald are exactly what the deleted `ops/run_pipeline.sh` existed to hand cron. Each side keeps exactly one branch: on Actions, the `DATABASE_URL` presence check, which earns it because otherwise `SmartCartDB()` falls back to the docker-compose default and the job dies 60 seconds later blaming Postgres.

    **`EnvironmentFile` is not a shell** (VM path): it parses `KEY=VALUE` literally, so the "password must be alphanumeric" warning `.env.example` used to carry is *gone* rather than documented. The flip side, noted in the file: values must not be quoted.

    **Two silent-failure guards, one per destination, and they are the point of this stage.** `.github/workflows/keepalive.yml` exists because GitHub disables scheduled workflows after 60 days without commits — and the schedule's own runs do not count as activity, so a paused project finds the sweep switched off with no error. On the VM the equivalent is `OnFailure=` firing `smartcart-alert@.service`, a `curl` to an ntfy.sh topic (the topic is effectively the secret, hence `.env` and not the unit file in the repo); **it must be tested on purpose**, because an alert that never fired does not exist.

    **`shared_buffers = 4GB` is load-bearing twice** (VM path, `ops/oracle/postgresql-smartcart.conf`). It is the share Postgres deserves on a dedicated box, *and* it is what stops Oracle reclaiming the instance: Always Free reclaims a VM whose CPU (95th percentile), network **and** memory all sit under 20% for 7 straight days. The nightly sweep cannot save it — 30 minutes a night is 3.5 hours out of 168 — but all three must hold at once, so 4 GB of 12 breaks the memory one permanently. The circulating alternative, a busy-loop burning CPU to fake activity, spends real resources, adds a process that can die silently, and buys nothing else.

    **There are no backups, and that is reasoned** — it is also what makes the two destinations cheap to switch between. The database is derived: a full sweep rebuilds `unified_products`, `store_products` and the embeddings in ~30 minutes, and runs nightly anyway. User data — cart and purchase history — lives in the browser's `localStorage`. So no `pg_dump` timer, no retention logic, no object-storage credentials, and **no data migration when the destination changes**: it is a `DATABASE_URL` edit and one sweep. This inverts the day anything user-owned lands in Postgres.

    **The public demo runs the API on Google Cloud Run (`Dockerfile`, `ops/demo-publica.md`) and the frontend on Vercel, with the database still on Neon.** The host is not a stylistic pick and the shortlist is shorter than it looks: the API loads `all-MiniLM-L6-v2` and peaks at **413 MB** RSS under `/optimize` (measured on the real container against Neon; 402 MB idle). Render's free tier gives 0,1 CPU and 512 MB — it fits by 100 MB but loads torch on every cold start at a tenth of a core; Koyeb no longer offers a clear free web service; and **Hugging Face Spaces, which this section used to recommend, moved the Docker and Gradio SDKs behind a paid plan** (only Static stays free, which cannot run a backend). Cloud Run gives real CPU, a comfortable 1 GiB and scale-to-zero inside a free tier of 180.000 vCPU-seconds, 360.000 GiB-seconds and 2M requests per month; it does require a card, which does not get charged inside that tier. Three things are load-bearing. **`CMD` must honour `$PORT`** — Cloud Run injects it and a hardcoded port fails the health check without ever naming the port; the `CMD` is in shell form for exactly that reason, since exec form does not expand variables. It installs **torch from PyTorch's CPU index before anything else**, because `pip install sentence-transformers` resolves torch from PyPI and that wheel drags the whole CUDA runtime along: measured, the image was **10,3 GB** for a model that runs on CPU, against 2,78 GB pinned. And it **downloads the model at build time**, which matters more here than it did on Spaces: with `--min-instances 0` the cold start is the *normal* case, not a rare one. The frontend stays on Vercel rather than being served from the same container: during a feedback week the frontend changes constantly, and that is a push (seconds) against an image rebuild with torch (~10 min).

    **There is no hard spending cap on Cloud Run**, so the bound is `--max-instances` (3) plus a budget alert — the alert notifies, it does not cut. Worth knowing before pointing anyone at the link. The remaining cost lever is the image itself: at 2,78 GB it also drives the cold start, and the honest fix is that the API uses torch **for exactly one thing at runtime** — encoding the `/search` query. Swapping it for ONNX Runtime would cut the image to ~600 MB and the RSS to ~250 MB, which is also the number that would unblock the 1 GB Oracle instance that `ops/README.md` records as rejected *because the model needs ~1,5 GB*. It is deliberately not done yet: it is gated on measuring the real cold start first, same doctrine as everywhere else here.

    **`SMARTCART_POOL_MIN_SIZE=0` is required on any deployment against Neon, and it is not a tuning knob.** Neon suspends the compute after 5 minutes *without activity*, and an open connection counts as activity — so `src/db_pool.py`'s `MIN_SIZE = 1` default holds one permanently, the database never suspends, and a 24/7 API burns ~1 CU-hour per hour: the free tier's 100 CU-hours are gone in a little over 4 days and the database shuts itself off mid-demo. `SMARTCART_POOL_MAX_IDLE` (60 s, against psycopg_pool's 10-minute default) is the other half: without it the last connection of a visit lives 10 minutes before Neon's own 5-minute timer even starts, i.e. 15 minutes billed per visit. What that trades away is one TCP+TLS handshake per fresh visit — milliseconds, once per session — which is the right side of the exchange, since exhausting the CU-hours takes the database down for everyone.

    **CORS is a real list now** (`src/api.py`). It was `allow_origins=["*"]` together with `allow_credentials=True`, which the CORS spec forbids and browsers reject — harmless while everything was localhost, an open door once the API is public. It reads `CORS_ORIGINS`, defaulting to the Vite dev-server ports.

    Exit codes are the monitoring contract: `0` all SUCCESS · `1` any PARTIAL/FAILED · `2` startup failure (Postgres unreachable — no scrapers ran, and no telemetry either, since there's nowhere to write it) · `143` SIGTERM, which is what a cancelled or timed-out job delivers and what lets the orchestrator close its open telemetry row instead of stranding it in `RUNNING`.

## Frontend architecture (`frontend/src`)

Plain React state (Context + `useReducer`/`useState`, no Redux/Zustand/React Query) and native `fetch` (no axios) — deliberate choices for an app this size; don't introduce a state/data-fetching library without a concrete reason. Tailwind is v4, configured CSS-first (theme tokens live in `src/index.css` under `@theme`, not in a `tailwind.config.js`/`postcss.config.js`, which don't exist in this project).

- `api/` — thin `fetch` wrappers per resource (`products.js`, `categories.js`, `optimize.js`) over `api/client.js`'s `apiFetch`/`ApiError`. `optimize.js`'s `optimizeCart()` deliberately catches the backend's 400 "infeasible" response and returns `{ok: false, detail}` instead of throwing, since that's an expected outcome the UI renders inline, not an error state.
- `context/` — `CartContext` (`{unified_id: {name, quantity}}`, persisted to `localStorage`, mirrors the shape the old Streamlit prototype used), `ProfileContext` (bank cards, memberships, and the geocoded `location`) and `HistoryContext` (see below). `ProfileContext` derives `coordinates` (null when the user skipped the address) for `POST /optimize`.

  **Delivery zone is derived, never asked.** There is no `profile.zone` and no zone dropdown — that selector was removed because it let a user hold an address in San Isidro while declaring "CABA", and the declared value is what priced the shipping. `utils/deliveryCosts.js`'s `resolveZoneFromAddress()` maps Nominatim's structured `address` (which `geocodeAddress()` had been requesting via `addressdetails=1` and discarding) onto one of the four zones, and `LocationModal` persists the result as `location.zone`. Its `PARTIDO_ZONES` table is **data, not logic**: a missing partido is a one-line fix. The three shapes it handles were relevered against live responses — CABA arrives as `state: "Ciudad Autónoma de Buenos Aires"`, GBA as `state: "Buenos Aires"` plus `state_district: "Partido de X"`, and sometimes GBA omits `state_district` and only has `city`. Returning `null` means "unknown", not an error: `getDeliveryCostsForZone()` already falls back to the first zone, which covers addresses outside AMBA, map-picked points whose reverse geocoding failed, and profiles saved before the field existed.

  The per-zone table is **not** dead weight next to `coto_logistics.py`: it is the *only* source of Día's and Carrefour's shipping cost (neither has a coverage or pricing endpoint at all), and Coto's fallback when there are no coordinates or its site is unreachable. Carrefour's number repeats across the four zones because its tariff really is flat, not because the rows are unfinished. `delivery_costs` must therefore keep travelling in the `POST /optimize` body with **all three** store keys — `src/optimizer.py` indexes `delivery_costs[store]` for every store in `min_spend_limits` (a missing key is a `KeyError`, not a default) and `find_strategic_swaps` hands the same dict back to the solver on its what-if run. The store list itself is derived from `DEFAULT_MIN_SPEND_LIMITS`, not from these keys — see the two-file rule in stage 6.
- **Address onboarding** — `components/onboarding/LocationModal.jsx` blocks the app from `App.jsx` whenever `profile.location` is falsy, geocoding through `api/geocoding.js` (Nominatim). The same modal doubles as the change-address flow, opened from the `MapPin` chip in `Header.jsx` and from `AddressField`'s "Cambiar" button in the cart's `ProfileDrawer` — those two are the only location controls in the app. (`AddressField` used to call a `clearLocation()` that wiped the address to force the *blocking* onboarding modal; both that helper and the trap it created — changing your mind left you with no address and no way out — are gone.) The `onClose` prop is the **only** thing that distinguishes the two modes: with it the modal is dismissable (X / Escape / backdrop) and preloads the current point onto the map; without it, onboarding stays blocking, because closing it there would leave the app in neither of the two valid states (an address, or `{skipped: true}`). `App.jsx` owns that open state so there is still exactly one place that knows how to geocode. Nothing extra is needed to re-filter the catalog after a change: `setLocation` always overwrites `storeCoverage`, which recomputes `unavailableStores`, which the grid already reads. Two constraints there are deliberate: the search fires on **explicit submit, never per keystroke** (Nominatim's policy is 1 req/s; an autocomplete violates it immediately and risks an IP ban), and it presents **multiple candidates for the user to pick** rather than auto-taking the first hit, since duplicate street names across partidos would otherwise silently bind the session to the wrong sucursal. The modal has an escape hatch ("seguir sin dirección"), because Nominatim being down must not render the app unusable; skipping stores `{skipped: true}`, which is distinct from `null` (never onboarded) and falls back to per-zone costs. Adding `location` did **not** version the `smartcart_profile_v1` localStorage key on purpose: pre-existing profiles simply lack the field, land on `undefined`, and get the modal — which is the desired behavior.
- `hooks/useProductFilters.js` — the participating stores live once in `utils/constants.js`'s `STORES` (id + label); `StoreAvailabilityToggle` draws the checkboxes from it and this hook derives the filter's neutral state from it, so adding a store is one entry rather than three hand-written key literals. All product-listing facets (brand, price range, store availability, sort) are derived 100% client-side over an already-fetched result array; there's no server round-trip per filter change (unlike the Carrefour reference this UI's layout is modeled on), so there's intentionally no "Apply" button. Price bounds/sorting go through `utils/formatters.js`'s `resolveDisplayPrice()` rather than raw `product.min_price`, so the grid sorts by the price it actually shows. That helper takes the cheapest `promo_unit_price ?? base_price` across `available_at_stores` and only falls back to `min_price` when no offer has a usable price — the order matters: `min_price` is list-price-only, so preferring it (as an earlier version did) hid every direct discount. (It used to be missing from `GET /search` altogether, which made the fallback mandatory there; `/search` now sends it, but the ordering is still the correct one.) `stripUnavailableStores()` nulls `min_price` **and `unit_price`** on a trimmed product and stays compatible with that fallback: the backend computes both over every offer and cannot know about coverage (it lives in `ProfileContext`), so on a product whose cheapest store does not deliver they describe an offer that is no longer listed. `formatUnitPrice()` no longer computes anything — it formats `product.unit_price` (`{value, base}`), which the backend now supplies. That move fixed two bugs with one cause: the client was dividing the wrong price (`min_price` is list-price-only, so the card showed a promo price beside a per-kilo figure from a different number) and on `GET /search` had no price to divide at all. The single kg/L base and the `null` cases live with `_build_unit_price` under stage 6.

- **Purchase history / "Comprar de nuevo"** — `context/HistoryContext.jsx` + `utils/purchaseHistory.js` + `components/history/`, mounted on `HomePage` and on `/carrito` **only when the cart is empty** (with products in it, it is noise next to the optimize flow). Written from `CartPage`'s `runOptimize` on the `response.ok` branch only — an infeasible cart is not a purchase and would pollute the ranking with carts the user could never buy.

  It is client-side **by construction**, not by simplification: the backend has no auth and no per-user table, and the closest thing to an identity (`anon_user_id`) travels to the analyzer and never comes back. Honest consequence: clearing site data loses the history.

  **The key `smartcart_history_v1` must never be bumped.** `ProfileContext`'s rule (don't version, migrate in an effect) already applies, but here it is stronger than a convention: the cart losing its contents costs the user five minutes of re-picking, while the history losing its contents costs months of signal **no user action can reconstruct**. New fields are tolerated-when-absent in `normalizeHistory()`, never by a `_v2`.

  **The session rule is the load-bearing decision.** One shopping session hits `/optimize` several times — accepting a suggestion re-optimizes on its own (`reoptimizeRef`), so does a strategic swap, so does undo, and "change a quantity and optimize again" is the normal flow. Appending one entry per run is not just noisy, it is biased in a specific direction: it over-weights exactly the carts the user fiddled with most, so one indecisive afternoon outranks three months of shopping. So an entry younger than `SESSION_WINDOW_MS` (30 min) is **replaced**, not appended — the last run is the one that most resembles what was actually bought, since it already includes the accepted swaps. SmartCart has no checkout (the user leaves for the chain's own site), so **no action means "I'm done"** and time is the only signal available. The window errs *short* on purpose: too short splits one session in two (a visible, self-limiting duplicate), too long merges two real purchases and **destroys the earlier one**, silently.

  **Four alternatives were considered and rejected**, recorded because each is tempting enough to be re-proposed: (a) **hashing the cart contents** to detect "the same cart again" fails exactly where it matters, since a swap changes the contents and swaps are the main source of repeat runs; (b) **counting each uid once per entry** does not help — what is duplicated is the entry, not the uid within it; (c) **an explicit "ya compré" button** is the cleanest signal of all, but it asks for an action at the precise moment the user has no reason to give it, so the feature would starve for data; (d) **recording on the checkout-link click** would systematically under-record Coto-heavy carts, since only the VTEX stores have a magic link — a bias along the *store* dimension, which is worse than the one it fixes.

  `MAX_ENTRIES = 20` is not only about size — it protects the *other two* keys: `useLocalStorage`'s write is a try/catch that swallows, so an unbounded history that eventually blows the shared origin quota would make the **cart** stop persisting with no error anywhere. That's why the trim lives inside `recordPurchase()` and not in the UI.

  Two UI rules that are easy to "simplify" into bugs: `useHabitualProducts` computes `missing` against the **raw** response, *before* `stripUnavailableStores` — the other order would report a product sold only by a non-delivering store as discontinued, the same class of lie the coverage warning below avoids; and "Repetir" **merges, it does not overwrite** (`cartOperations.mergeItems`, one write, not N `addItem` calls). `restoreItems` would be shorter but the same button also lives on the home page, where the cart may be full: a button that means "add" on one screen and "discard everything" on another is worse than either. The habituales ranking counts **purchases, not units** (6 yogurts once is not a habit; 1 yogurt on 6 trips is) and requires ≥2 — so a user with a single stored cart sees the list but no grid, which is handled by hiding the grid, never by lowering the threshold. Delisted products are **never purged** from the history: the pruner is the store's doing, not the user's, the product can come back, and the ranking is not reconstructible.

- **Cart line prices and estimated subtotal** — `hooks/useCartProducts.js` + `context/CartProductsContext.jsx` + `components/cart/CartLineItem.jsx` + `components/cart/EstimatedSubtotal.jsx`. `CartContext` stores only `{name, quantity}`, so image and price are resolved through `POST /products/by-ids` (the same endpoint the history already uses — no new endpoint), stripped by coverage exactly like the grid, and **failing open**: if the request dies the cart draws as it did before, name and quantity, because the user already knows what they picked.

  **The fetch and the subtotal calculation live in `CartProductsContext`, one level, shared by `CartPage` and `CartDrawer`.** `useCartProducts` has no cache of its own — every call site fires its own `POST /products/by-ids` — so if both consumers called it independently, the one route where they can coexist (`/carrito`, drawer opened over the page) would double the request on every cart change. The provider sits between `ProfileProvider` and `HistoryProvider` in `main.jsx`, because `useCartProducts` needs `useProfile()` (for coverage stripping) and `CartProvider` sits outside `ProfileProvider` — so the aggregation can't live in `CartContext` itself.

  **This deliberately breaks the rule `CartContext.jsx` documents** ("el carrito no muestra subtotal antes de optimizar"). The reason is that a list of names with no price at all leaves the question *"how much am I carrying?"* unanswered on the exact screen where it gets asked, and every tester asks it. The honest form is cheaper than the silence: the number is labelled an **estimate** and the copy says what it is — the cheapest price of each product taken separately, which is a cart nobody can actually buy (it spans three chains) and which ignores delivery, bank discounts and quantity promos. It is a floor, not the total; `/optimize` computes the total. It renders **only when every line has a price** (`null` otherwise), because a subtotal over half the cart is worse than no subtotal. Measured on the demo cart: $67.338 estimated against $68.737 optimized, i.e. close enough not to confuse and honestly on the low side. `CartDrawer` (opened from the header's cart button, on every route) shows the same figure, so the running total is visible while still adding products, not only once the user reaches `/carrito`.

- **Cart coverage warning** — `hooks/useUnavailableCartItems.js` + `components/cart/CoverageWarning.jsx` tell the user which cart items only exist at a store that can't deliver. `CartContext` stores just `{name, quantity}`, so the store map comes from reusing `POST /price-preview` (whose response is already keyed `unified_id → store_id`), and only when `unavailableStores` is non-empty — the common case costs zero requests. Two rules: it **never mutates the cart** (a mistyped address must not delete what the user picked; the optimizer reports the same products as `unavailable_products` anyway), and a `unified_id` **absent** from the response is not flagged — `/price-preview` filters by `in_stock`, so absence means "out of stock everywhere", not "doesn't reach you".
- `components/megamenu/` — two levels (section → shelf) fed by `useShelves()` over `GET /categories`, and **every** click routes to `/categoria/:shelf` (→ `GET /category/{slug}`). There is no routing rule left to get wrong. `sectionIcons.js` maps the four sections by exact name — the file it replaced needed 18 regexes to cover top-levels the catalog never had — and falls back to a generic icon, so a new section cannot break the menu.
- `components/optimize/` — renders `POST /optimize`'s response. `SavingsPanel` is the header: the total spent, and beside it the saving from `price_savings.total` — **drawn only when it is `> 0`**, since every product coming from a single store is a legitimate zero and a green `$0` is noise, not a result. The saving itself is a single line ("Ahorrás $X usando el sitio"); what the number is compared against (the most expensive store carrying each product, shipping and bank discounts excluded) is not decoration but it no longer sits in a fixed paragraph — it lives one click away in the existing "Ver de dónde sale" detail, so it's there for whoever asks without being noise for whoever doesn't. See stage 6 for why it is not comparable against `total_spent_net`. `LogisticsNotice` reads the `logistics.coto` block, but **only renders when there's something to act on**: excluded/not-covered, or `source: "fallback"` (an estimated shipping cost must never be displayed as if it were the live tariff). The normal case — Coto covers, real tariff — renders nothing, since the per-store breakdown already shows which stores are in the split and at what cost.
- **Home page** (`pages/HomePage.jsx`) — three steps, a *"Probar con un carrito de ejemplo"* button over `GET /demo-cart`, and the shelves grouped by section. It used to be a headline plus all 49 shelf pills flattened into one cloud (`useShelves` exposes `sections`; the home was the only caller that threw the grouping away), which said neither what the app does nor where to start. That is fatal for asynchronous feedback specifically: the tester has to build a cart from scratch before reaching the split. The button merges (`mergeItems`), never replaces — the home can be visited with a full cart, same rule as the history's "Repetir".

- Routes (`App.jsx`): `/` (home), `/buscar` (search results, reads `?q=`), `/categoria/:bucket` (category results), `/carrito` (cart + profile inputs + optimize flow, in that order since profile fields are only consumed at optimize-time).
